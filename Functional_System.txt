======================================================================
0. НАЗНАЧЕНИЕ ДОКУМЕНТА И ПРАВИЛА ЧТЕНИЯ
======================================================================

Этот документ описывает Voxygen как целую систему: пользовательский интерфейс, серверную логику, Telegram-интеграцию, базу данных, систему территорий и рейтингов, городское управление, экономику, визуальную кастомизацию, события и подсистему интерактивной карты.

Документ составлен по текущим исходным файлам репозиториев, а не только по ранее подготовленному описанию карты. Если поведение интерфейса, настройки инфраструктуры или внешние секреты нельзя подтвердить чтением репозитория, это отдельно отмечается. Наличие имени секрета в коде не означает, что его значение или работоспособность настройки были проверены.

Главные исходные файлы:
- CounterBoard/Voxygen/src/App.jsx — пользовательское приложение и большая часть клиентской логики.
- CounterBoard/Voxygen/src/main.jsx — запуск React-приложения и инициализация Telegram Web App.
- CounterBoard/Voxygen/bot/src/worker.js — основной backend Worker, API, Telegram webhook, бизнес-логика и миграции D1.
- CounterBoard/Voxygen/bot/schema.sql — базовая схема D1; фактическая схема шире и дополняется миграциями Worker.
- CounterBoard/Voxygen/shared/world-map-coordinates.js — общая геометрия мира и функции координат/масштаба.
- CounterBoard/Voxygen-map-assets/tools/build_map.py — генератор Deep Zoom.
- CounterBoard/Voxygen-map-assets/.github/workflows/publish-map.yml — автоматическая обработка и публикация карты.
- CounterBoard/Voxygen-map-assets/public/_headers — HTTP-заголовки статических ресурсов.
- CounterBoard/Voxygen-map-assets/wrangler.jsonc — конфигурация Worker статических ресурсов.

Документация описывает именно текущую архитектуру. Она не является инструкцией по восстановлению секретов и не содержит секретных значений.

======================================================================
1. ОБЩАЯ АРХИТЕКТУРА
======================================================================

Voxygen — Telegram Mini App с React-интерфейсом, серверной логикой на Cloudflare Workers и постоянными данными в Cloudflare D1.

В системе используются три Cloudflare Worker, три GitHub-репозитория и одна основная база Cloudflare D1.

1.1. Worker voxygenebot — публикация пользовательского интерфейса

Адрес:
https://voxygenebot.counterboard.workers.dev

Назначение:
- отдача собранного фронтенда Voxygen;
- загрузка HTML, JavaScript и остальных статических файлов приложения;
- запуск интерфейса внутри Telegram Web App;
- отображение разделов приложения и интерактивной карты.

Конфигурация:
CounterBoard/Voxygen/wrangler.jsonc

Основные параметры:
- name: voxygenebot;
- assets.directory: ./dist.

Сборка фронтенда выполняется Vite. Результат сборки помещается в dist и публикуется как статические Assets Worker.

1.2. Worker voxygen — основной backend

Адрес:
https://voxygen.counterboard.workers.dev

Назначение:
- проверка Telegram Web App Init Data;
- определение пользователя и его роли;
- предоставление API для всех основных функций приложения;
- управление территориями, пользователями, рейтингами и комментариями;
- городское управление, приглашения и роли жителей;
- казна, персональные балансы и финансовые операции;
- каталог визуальных предметов и достижения;
- события и напоминания;
- настройки пользователя и глобальные настройки;
- загрузка исходной карты в GitHub Releases;
- выдача исходной карты в резервном режиме;
- обработка Telegram webhook и команд банковского пользователя.

Исходный файл:
CounterBoard/Voxygen/bot/src/worker.js

Конфигурация:
CounterBoard/Voxygen/bot/wrangler.toml

1.3. Worker voxygen-map-assets — публикация графических ресурсов карты

Адрес:
https://voxygen-map-assets.counterboard.workers.dev

Назначение:
- выдача manifest.json;
- выдача preview.webp;
- выдача Deep Zoom WebP-тайлов;
- обслуживание запросов статических файлов;
- CORS и cache headers.

Worker публикует каталог public репозитория CounterBoard/Voxygen-map-assets через Workers Static Assets.

1.4. GitHub-репозитории

Основной репозиторий:
CounterBoard/Voxygen

Содержит:
- React-приложение;
- основной backend Worker;
- SQL-базовую схему D1;
- общие функции геометрии карты;
- тесты;
- конфигурации Workers и Vite.

Репозиторий обработки карты:
CounterBoard/Voxygen-map-assets

Содержит:
- скрипт генерации Deep Zoom;
- GitHub Actions workflow обработки карты;
- конфигурацию voxygen-map-assets Worker;
- правила HTTP-заголовков;
- документацию контракта загрузчика карты.

Репозиторий исходников карты:
CounterBoard/Voxygen-map-storage

Используется для хранения оригиналов карты как GitHub Release Assets. Это не репозиторий исходного кода приложения.

Release tag:
world-map

1.5. Cloudflare D1

Имя базы:
voxygen

Binding в основном Worker:
DB

D1 является постоянным хранилищем структурированных данных приложения. В ней находятся пользователи, территории, роли, оценки, комментарии, городские связи, экономика, события, настройки и ссылки на исходник карты.

D1 не используется для хранения Deep Zoom-тайлов. Готовые тайлы и превью публикуются как статические ресурсы отдельного Worker.

1.6. Общий маршрут запросов

Пользователь открывает Telegram Mini App:
Telegram → voxygenebot → React-приложение.

Когда приложению нужны данные:
React-приложение → voxygen API → проверка Telegram Init Data → D1 / Telegram Bot API / GitHub API.

Для карты:
React-приложение → voxygen-map-assets → manifest и preview → необходимые тайлы.

Для загрузки новой карты:
Главный инспектор → voxygenebot → voxygen → GitHub Release → GitHub Actions в Voxygen-map-assets → генерация Deep Zoom → публикация в voxygen-map-assets → обновлённый manifest → клиент.

2. ФРОНТЕНД И ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС
======================================================================

2.1. Технологии

Фронтенд использует:
- React 18;
- React DOM;
- Vite 6;
- lucide-react для иконок.

Основные команды package.json:
- npm run dev — локальный режим разработки;
- npm run build — сборка фронтенда в dist;
- npm run preview — локальный просмотр собранной версии;
- npm test — запуск тестов Node.js.

Точка входа:
src/main.jsx

Она сообщает Telegram Web App, что приложение готово, вызывает expand() и монтирует React-компонент приложения.

Основная реализация интерфейса находится в одном крупном файле:
src/App.jsx

2.2. Адреса backend и карты

В клиентском коде заданы:
API_BASE = https://voxygen.counterboard.workers.dev
MAP_ASSETS_BASE = https://voxygen-map-assets.counterboard.workers.dev

Фронтенд напрямую обращается к основному API и к Worker картографических ресурсов.

2.3. Основная навигация

Нижняя навигация содержит четыре раздела:

1. Визуал
   Каталог визуальных предметов, инвентарь, покупка, оформление территорий и управление предметами в пределах прав пользователя.

2. Территории
   Основной раздел с тремя внутренними вкладками:
   - Набор — список открытых объявлений о наборе жителей;
   - Карта — интерактивная карта с маркерами территорий;
   - Рейтинг — список территорий, отсортированный по рейтинговым показателям.

3. Ивенты
   Список событий, создание и управление событиями в соответствии с ролью пользователя, напоминания.

4. Профиль
   Minecraft-никнейм и статус его подтверждения, персональные настройки, данные городов пользователя, городское управление, доступные административные инструменты.

2.4. Карточка территории

Карточка/страница территории объединяет сведения о городе и инструменты взаимодействия:
- название и координаты;
- владелец, основатели/мэры и жители;
- рейтинг и оценки;
- комментарии и ответы;
- скриншоты;
- дополнительная информация;
- объявление о наборе;
- казна и финансовые действия;
- управление городом;
- визуальное оформление города.

Конкретный набор действий зависит от роли пользователя и его отношения к выбранной территории.

2.5. Стилизация текста Minecraft

В интерфейсе есть обработка форматирования Minecraft:
- цветовые коды;
- жирный, курсивный, подчёркнутый и зачёркнутый текст;
- обфускация;
- шестнадцатеричные цветовые коды.

Это применяется к названиям и текстам, где допустимо Minecraft-форматирование. Отдельно реализована обработка Telegram username и ссылок на Telegram.

3. АВТОРИЗАЦИЯ, ПОЛЬЗОВАТЕЛИ И РОЛИ
======================================================================

3.1. Авторизация через Telegram

Клиент получает Telegram Web App Init Data из Telegram WebApp API.

Для API-запросов Init Data передаётся:
- обычно через заголовок X-Telegram-Init-Data;
- для некоторых JSON-запросов также может присутствовать в поле initData.

Основной Worker использует BOT_TOKEN и функцию verifyInitData().

Проверка включает:
1. разбор параметров Init Data;
2. извлечение hash;
3. сортировку параметров;
4. формирование data-check-string;
5. вычисление HMAC-SHA-256 по алгоритму Telegram Web Apps;
6. сравнение рассчитанной подписи с переданной;
7. разбор JSON-поля user.

При отсутствии корректной подписи запрос не считается авторизованным.

Ограничение: текущая verifyInitData() проверяет подпись и наличие user, но не проверяет свежесть auth_date. Поэтому срок действия ранее подписанного Init Data не ограничивается самим Worker. getCurrentUser() также поддерживает передачу initData через query string, хотя штатный путь клиента — заголовок X-Telegram-Init-Data или поле JSON. Эти особенности отмечены в разделе 30.

3.2. Роли

В системе используются три основные роли:

Пользователь (user):
- обычный участник приложения;
- может просматривать доступные территории;
- после подтверждения Minecraft-ника получает доступ к действиям, для которых требуется verified-профиль;
- может вступать в города, оценивать территории и участвовать в разрешённых пользовательских функциях.

Инспектор (inspector):
- роль хранится в таблице inspectors;
- имеет доступ к инспекторским функциям, включая инспекторские оценки;
- не равнозначен главному инспектору.

Главный инспектор (main_inspector):
- определяется через INSPECTOR_CHAT_ID;
- настройка может содержать Telegram ID либо username;
- имеет расширенные административные права;
- управляет инспекторами, территориями, пользователями, глобальными настройками и публикацией карты;
- некоторые административные операции доступны исключительно этой роли.

Проверки прав выполняются на backend. Скрытие кнопки в интерфейсе не является единственным механизмом защиты.

3.3. Подтверждение Minecraft-ника

В профиле пользователь указывает Minecraft-никнейм.

Сервер хранит:
- Telegram ID;
- Telegram username;
- Minecraft nickname;
- статус пользователя;
- при наличии — XUID;
- идентификатор текстуры скина;
- время проверки скина.

Для ряда действий используется requireVerifiedUser(): кроме корректной Telegram-авторизации требуется подтверждённый статус и непустой Minecraft-никнейм.

Поддерживается предварительная регистрация пользователей с Minecraft-ником и Telegram username. При подтверждении соответствующего аккаунта сервер может связать его с предварительно зарегистрированными данными.

Получение игровых идентификаторов и скина:
- для Bedrock/Xbox основным источником служит GeyserMC: сначала поиск XUID по нику, затем получение skin texture по XUID;
- если подходящая текстура не найдена, выполняется Java fallback через Minecraft Services и резервные Mojang name lookup endpoints, затем через Mojang Session Server;
- в users сохраняются XUID, идентификатор текстуры и время последней проверки;
- сохранённая текстура повторно используется до истечения шестичасового интервала обновления;
- при временной ошибке внешнего сервиса ранее найденная текстура не стирается; неизвестный профиль не превращается автоматически в стандартный скин Steve;
- для отображения аватара используется mc-heads.net по проверенному texture ID.

3.4. Синхронизация Telegram username

Worker синхронизирует Telegram username пользователя в таблице users и связанных записях. При обработке сообщений и callback_query webhook обновляет сведения об отправителе.

Username используется как контактная информация и как один из способов разрешения имени пользователя, но основным идентификатором аккаунта остаётся Telegram ID.

3.5. Права основателя и мэра

Владелец территории определяется по owner_telegram_id.
Дополнительные управляющие хранятся в territory_managers.

Функция isTerritoryManager() считает управляющим:
- владельца утверждённой территории;
- пользователя, присутствующего в territory_managers.

Основатель и мэр могут управлять городом в пределах серверных проверок.

3.6. Жители и членство в нескольких городах

Членство хранится в city_memberships с составным ключом:
telegram_id + territory_id.

Схема поддерживает принадлежность одного пользователя к нескольким территориям. В Worker предусмотрена миграция со старой схемы одиночного членства.

Для приглашений используется city_invites. Приглашение может быть отправлено уже зарегистрированному пользователю или сохранено до подтверждения Minecraft-ника адресата.

======================================================================
4. ТЕРРИТОРИИ: СОЗДАНИЕ, ПРОВЕРКА И УПРАВЛЕНИЕ
======================================================================

4.1. Создание территории

Клиент отправляет данные через:
POST /api/territories

Обычный пользователь должен иметь подтверждённый Minecraft-никнейм. Главный инспектор может создавать территорию напрямую.

Проверяются:
- название;
- данные владельца;
- координаты X и Z;
- допустимый диапазон координат;
- длина текстовых полей.

Допустимые координаты:
Фактический диапазон системы:
X: от -3008 до 3007 включительно;
Z: от -3008 до 3007 включительно.

Обычная заявка получает статус pending. Территория, созданная главным инспектором, может сразу получить статус approved.

4.2. Telegram-процесс утверждения

Для заявок обычных пользователей Worker отправляет сообщение главному инспектору через Telegram Bot API.

Главный инспектор может начать процесс утверждения через inline-кнопку. Затем Worker создаёт сессию territory_approval_sessions и запрашивает сообщение из трёх строк:
1. название территории;
2. @username основателя/мэра;
3. X Z — две координаты.

Для государственной территории вместо username используется специальное значение Multi-Punk.

После проверки сервер сохраняет утверждённую территорию. Callback-действия по утверждению/отклонению проверяются по роли главного инспектора.

4.3. Государственные территории

У территории есть признак is_government.

Государственные территории имеют отдельные ограничения:
- некоторые функции городского управления для них недоступны;
- они используют соответствующий тип маркера;
- обычные пользователи не могут создавать от имени государственной территории некоторые виды событий;
- оформление обычного города не применяется к государственной территории.

4.4. Административные операции с территориями

Главный инспектор может:
- переименовать территорию;
- удалить территорию;
- изменить координаты;
- изменить владельца;
- изменить управляющего/мэра;
- управлять заявками и инспекторами.

Серверные маршруты этих действий находятся в группе /api/admin/territories/*.

4.5. Дополнительная информация

Основатель или мэр утверждённой негосударственной территории может сохранить дополнительную информацию через:
POST /api/city/additional-info

Максимальная длина поля в текущем backend:
542 символа.

Для государственной территории поле недоступно.

======================================================================
5. ГОРОДСКОЕ УПРАВЛЕНИЕ И ПРИГЛАШЕНИЯ
======================================================================

5.1. Управление жителями

Основатель/мэр может:
- приглашать пользователя в город;
- отменять приглашение;
- удалять жителя;
- назначать жителя мэром/управляющим;
- снимать полномочия мэра;
- просматривать список жителей, управляющих и приглашений.

Основные маршруты:
- POST /api/city/invite
- POST /api/city/invite/cancel
- POST /api/city/remove-resident
- POST /api/city/promote-resident
- POST /api/city/demote-manager
- POST /api/city/leave
- GET /api/city/management

5.2. Приглашения

Приглашения отправляются через Telegram Bot API с кнопками согласия и отказа.

Если Minecraft-ник ещё не связан с подтверждённым пользователем, приглашение может быть сохранено в ожидании подтверждения ника. После появления подходящего аккаунта Worker может отправить приглашение.

Существуют приглашения типа join и transfer. Состояние приглашения хранится в city_invites.

5.3. Изменение состава управляющих

Изменение управляющего может требовать процедуры согласования между текущими основателями/мэрами территории.

Для этого используются:
- manager_change_requests;
- manager_change_votes.

Запрос имеет статус, инициатора, целевого пользователя, срок действия и параметры голосования. Срок голосования — 24 часа. Инициатор учитывается как один голос за предложенное изменение; остальные действующие управляющие голосуют через Telegram callback. Для одобрения требуется больше половины голосов от общего состава управляющих, включая инициатора. Если срок истёк или все остальные управляющие проголосовали без достижения большинства, запрос отклоняется. При единственном управляющем повышение жителя может быть выполнено сразу; понизить последнего управляющего нельзя.

5.4. Уход из города

Пользователь может покинуть территорию через соответствующий маршрут. Сервер проверяет текущие отношения пользователя с территорией и применяет правила членства/управления.

======================================================================
6. РЕЙТИНГ ТЕРРИТОРИЙ
======================================================================

6.1. Критерии

Оценка территории состоит из четырёх параметров:
- integrity;
- comfort;
- atmosphere;
- detail.

Каждый параметр принимает целое значение от 1 до 5.

Итоговая оценка одной анкеты:
(integrity + comfort + atmosphere + detail) × 0.5

Максимальный итог одной анкеты — 10 баллов.

6.2. Два потока оценок

Оценки обычных пользователей хранятся в ratings.
Оценки инспекторов хранятся отдельно в inspector_ratings.

Оценка обычного пользователя требует подтверждённого Minecraft-ника.

Основатель/мэр территории не может оценивать собственный город как обычный пользователь. Для инспекторской роли действует отдельная ветка расчёта.

6.3. Вес жителей

Если пользователь является жителем оцениваемой территории, его оценка получает вес 1/3. Оценка пользователя, не являющегося жителем, получает обычный вес 1.

6.4. Учёт свежих оценок

Оценки сортируются от новых к старым.

Для инспекторской оценки:
- последние две оценки образуют группу новых;
- остальные — группу старых;
- если есть старые оценки, среднее новых и среднее старых получают по 50% веса.

Для пользовательской оценки:
- последние пять оценок образуют группу новых;
- остальные — группу старых;
- при наличии обеих групп они получают по 50% веса.

Внутри каждой группы применяется вес оценки жителя, если он относится к территории.

6.5. Ограничение частоты

Повторное обновление оценки одним пользователем для одной территории ограничено интервалом 20 часов.

Если ограничение ещё действует, API возвращает HTTP 429, время следующей попытки и ранее сохранённые значения оценки.

6.6. Сортировка

Экран рейтинга использует рассчитанные показатели территории. Backend возвращает данные рейтинга и число пользовательских голосов.

7. КОММЕНТАРИИ, ОТВЕТЫ И СКРИНШОТЫ

7.1. Комментарии

Для территорий поддерживаются:
- получение списка комментариев;
- добавление комментария;
- редактирование;
- удаление;
- ответы на комментарии;
- редактирование и удаление ответов.

Основные таблицы:
- comments;

Сервер хранит Telegram ID автора, username (если доступен), текст, роль и время создания.

7.2. Скриншоты

Пользователь может отправить скриншот территории.

В таблице screenshots сохраняются:
- ID;
- территория;
- Telegram ID и username отправителя;
- Telegram file_id и file_unique_id;
- статус;
- время создания;
- данные модерации.

Поддерживаются получение, выдача файла, модерация и удаление скриншотов. Для взаимодействия с Telegram используются file_id и Telegram Bot API.

Обычные пользовательские загрузки получают статус pending и отправляются управляющим через Telegram. Скриншоты государственных территорий, а также загрузки инспекторов и главного инспектора могут сразу получать статус approved. Публичная выдача включает только одобренные изображения.

В Worker также существует POST /api/screenshots/{id} для HTTP-модерации. В текущей маршрутизации этот путь передаёт обработчику не все аргументы, поэтому HTTP-одобрение не работает; штатный интерфейс использует Telegram callback-модерацию. Подробности приведены в разделе 30.

- POST /api/recruitment

======================================================================
9. СОБЫТИЯ И НАПОМИНАНИЯ
======================================================================

9.1. События

События хранятся в таблице events.

Данные события включают:
- название;
- связанную территорию (если есть);
- место;
- дату и время;
- координаты;
- описание;
- изображение;
- внешнюю ссылку;
- часовой пояс события;
- автора;
- время создания и обновления;
- активность.

Основные маршруты:
- GET /api/events
- POST /api/events
- PATCH /api/events
- DELETE /api/events

Обычный пользователь может создавать событие от территории, если является её основателем/мэром или жителем. Для государственной территории действуют отдельные ограничения. Главный инспектор имеет расширенные права.

Если территория выбрана, место события берётся из её проверенного названия, а не доверяется произвольному тексту клиента.

Создание использует requestKey в связке с Telegram ID автора и SHA-256 хэшем содержимого. Повтор того же ключа с тем же содержимым возвращает уже созданное событие; тот же ключ с изменённым содержимым даёт конфликт HTTP 409. Клиент App.jsx передаёт стабильный requestKey для сетевых повторов. Если старый внешний клиент не передал ключ, Worker генерирует новый UUID.

Изменять событие может его создатель или главный инспектор; прошедшие события редактировать нельзя. Если меняется eventAt, обновление события и пересчёт времени напоминаний выполняются одним D1 batch. Удаление события является soft delete: active устанавливается в 0, ожидающие и отправляющиеся напоминания отменяются.

9.2. Напоминания

Пользователь может создать или удалить напоминание о событии:
- POST /api/events/reminder
- DELETE /api/events/reminder

Таблица event_reminders хранит:
- событие и пользователя;
- величину и единицу времени до события;
- рассчитанное время отправки;
- статус;
- количество попыток;
- время следующей попытки;
- claim token;
- время успешной отправки.

Для пары event_id + telegram_id действует уникальность: один пользователь имеет одно напоминание на событие. Повторная настройка обновляет существующую запись. Напоминание можно создать только для активного будущего события и если рассчитанное время отправки ещё не наступило.

9.3. Фоновая обработка

В bot/wrangler.toml установлен Cron:
* * * * *

То есть scheduled handler запускается каждую минуту.

Он:
- проверяет напоминания, которые пора отправить;
- отправляет уведомления через Telegram Bot API;
- обрабатывает повторные попытки;
- удаляет устаревшие события;
- удаляет старые записи идемпотентности создания событий.

За один запуск выбирается не более 50 ожидающих напоминаний. Запись в статусе sending, не обновлявшаяся более пяти минут, считается зависшей и возвращается в очередь с увеличением attempts. Повторы используют экспоненциальную задержку с ограничением до 30 минут. После восьми неудачных попыток задача переводится в failed; ошибки Telegram с кодами 400, 401 и 403 считаются постоянными и не повторяются.

События, завершившиеся более чем 24 часа назад, очищаются. Напоминания удаляются перед удалением соответствующих событий. Записи event_create_requests старше 30 дней также очищаются.

Важно: purgeExpiredEvents() вызывается не только из scheduled handler, но и непосредственно при GET /api/events. Поэтому чтение календаря также может запускать очистку и изменять D1.

9.4. Защита от повторного создания

При создании события используется requestKey и хэш содержимого запроса. Это позволяет распознавать повторную отправку одного и того же действия при сетевых повторах.

10. ВИЗУАЛЬНАЯ КАСТОМИЗАЦИЯ И ДОСТИЖЕНИЯ
======================================================================

10.1. Каталог предметов

Система визуальных предметов позволяет создавать, покупать, хранить и использовать оформление.

Основные таблицы:
- customization_categories;
- customization_items;
- user_items;
- city_items;
- city_customization.

Предметы имеют категории, названия, цену, изображение, активность и дополнительные признаки. Для предметов могут задаваться теги/категории, сортировка и видимость.

10.2. Управление каталогом

Главный инспектор имеет инструменты создания и редактирования визуальных предметов:
- создание предмета;
- редактирование;
- удаление;
- включение/выключение видимости;
- сортировка предметов;
- сортировка тегов/категорий;
- управление категориями и специальными признаками маркеров.

Изображения предметов выдаются через API Worker. При создании и редактировании сервер проверяет тип и допустимые характеристики изображения.

10.3. Персональные предметы и баланс

У пользователя есть баланс самоцветов и приобретённые предметы.

Баланс хранится в user_currency.
Приобретённые предметы — в user_items.

10.4. Оформление города

Город может использовать:
- маркер территории;
- фон/элемент оформления.

Настройки города хранятся в city_customization. Менять оформление могут основатель и мэры. Для государственных территорий обычное городское оформление недоступно.

Маркер проверяется по совместимости с типом территории: обычный или государственный.

10.5. Достижения

Система достижений оценивает требования территории и может автоматически выдавать визуальные награды.

Используются:
- функция расчёта условий;
- проверка требований;
- повторная проверка достижений;
- таблица achievement_awards для фиксации выданных наград.

Главный инспектор может инициировать повторную проверку через:
POST /api/achievements/recheck

10.6. Проверки каталога и жизненный цикл предмета

Создавать, редактировать, удалять и сортировать предметы/теги, а также менять hidden_from_users может только главный инспектор.

При создании и редактировании проверяются:
- непустое название и хотя бы один тег;
- цена — целое безопасное число, не меньше нуля;
- изображение должно начинаться с data:image/ и иметь размер не более 1 000 000 символов;
- цвет выбирается из фиксированного набора: none, red, orange, yellow, green, turquoise, blue, purple, magenta, white, black;
- предмет с тегом «Обложка» должен иметь соотношение сторон 8:3;
- governmentMarker разрешён только для предмета с тегом «Метка» или «Обложка»;
- включённое достижение должно содержать хотя бы один корректный неотрицательный порог.

Удаление предмета является мягким: customization_items.active устанавливается в 0. Перед этим ссылки на предмет очищаются из city_customization, а записи city_items удаляются. История achievement_awards намеренно сохраняется, чтобы повторное создание/проверка не отправляли основателю повторное уведомление о ранее выданном достижении. Персональные строки user_items при удалении предмета не удаляются, но неактивный предмет не попадает в обычный каталог активных предметов.

10.7. Изображения, государственные визуалы и автоматический маркер

Изображение предмета обслуживается отдельным маршрутом GET /api/customization/items/{id}/image. Обработчик читает data URL из customization_items, декодирует Base64 и отдаёт исходный MIME type. Ответ содержит Cache-Control: public, max-age=300 и X-Content-Type-Options: nosniff. Сам обработчик не требует Telegram-авторизации и не проверяет hidden_from_users или active; идентификатор предмета служит адресом ресурса, а не полноценным механизмом контроля доступа. Флаг hidden_from_users ограничивает отображение в каталоге и покупку обычными пользователями, но не является защитой содержимого изображения.

Для обычной территории маркер может быть взят из city_items либо из личного инвентаря основателя, управляющего или жителя. Для установки сервер проверяет право управляющего, активность предмета, тег «Метка», отсутствие признака government_marker и факт владения одним из участников города или самим городом. Обложка проверяется аналогично по тегу «Обложка».

Если у обычного города не выбран допустимый маркер, ensureFirstCityMarker() подбирает самый ранний доступный визуал с тегом «Метка»: сначала учитывается acquired_at, затем sort_order и ID предмета. Для государственного города обычный пользовательский маркер автоматически не подбирается.

Государственные визуалы создаются главным инспектором с governmentMarker=true и соответствующим тегом. syncGovernmentVisual() назначает такой визуал всем одобренным государственным территориям: маркер и обложка синхронизируются отдельно. При снятии государственного признака или удалении соответствующего тега ссылки на этот предмет у государственных территорий очищаются. Обычный endpoint изменения городского оформления для государственных территорий запрещён.

11. САМОЦВЕТЫ, ЛИЧНЫЙ БАЛАНС И КАЗНА ГОРОДА
======================================================================

11.1. Балансы

Личный баланс:
user_currency

Казна территории:
city_treasury

Операции:
financial_operations

Дополнительный журнал Telegram-банковских операций:
bank_transactions

11.2. Пополнение казны

Маршрут:
POST /api/treasury/deposit

Пополнять казну могут участники соответствующей территории, включая управляющих, при соблюдении серверных проверок.

11.3. Пожертвование

Маршрут:
POST /api/treasury/donate

Пожертвовать может любой авторизованный пользователь, даже если он не состоит в целевой территории. Территория должна быть одобренной, негосударственной и иметь хотя бы одного управляющего. Сумма списывается с личного баланса пользователя и зачисляется в city_treasury.

11.4. Снятие средств

Маршрут:
POST /api/treasury/withdraw

Снимать средства из казны может основатель или мэр соответствующей территории. Сервер проверяет наличие средств.

11.5. Идемпотентность

Финансовые операции используют operationId и запись в financial_operations. Это нужно, чтобы повторный запрос после потери ответа не списывал средства повторно.

На клиенте незавершённый токен операции сохраняется в localStorage/sessionStorage, когда это возможно. Пока исходная операция не подтверждена, клиент блокирует отправку изменённой суммы для того же действия и получателя.

11.6. Telegram-банковский пользователь

В Worker предусмотрен отдельный режим банковского пользователя, задаваемый секретом BANKER_TELEGRAM_ID. Проверка сравнивает message.from.id с настроенным значением. Команда может быть направлена на игрока, определяемого по Minecraft-нику/Telegram username, либо на одобренную территорию, определяемую по названию.

Парсер поддерживает несколько вариантов порядка аргументов: сумма и получатель либо получатель и сумма; положительная сумма означает зачисление, отрицательный знак — списание. Также распознаётся специальное текстовое уведомление о переводе с суффиксом (88). Допустимая сумма — положительное целое число не более 1 000 000 000.

Для игрока команда изменяет user_currency; для территории — city_treasury. Списание выполняется только при достаточном балансе. После успешной операции Worker сохраняет целевой Telegram ID (для игрока), баланс после операции, направление и статус, отвечает в чат и отправляет уведомление получателю или управляющим территории.

Повторные Telegram update_id не должны приводить к повторному проведению одной операции: update_id имеет UNIQUE-ограничение в bank_transactions. Однако регистрация операции, изменение баланса и запись итогового статуса не объединены в одну транзакцию; особенности обработки сбоя описаны в finding 30.16.


11.7. Механика финансовых переводов

Для POST /api/treasury/deposit, POST /api/treasury/donate и POST /api/treasury/withdraw используется общая функция executeIdempotentFinancialTransfer().

Ключ операции:
- operationId нормализуется и допускает только символы A-Z, a-z, 0-9, точку, подчёркивание, двоеточие и дефис;
- допустимая длина — от 8 до 120 символов;
- если ключ не передан, backend создаёт UUID для совместимости со старыми клиентами; такой запрос не получает устойчивой клиентской идемпотентности при повторной отправке;
- financial_operations хранит operation_id, Telegram ID инициатора, тип операции, целевую территорию, сумму, статус и временные метки;
- повтор с тем же ключом и теми же параметрами возвращает сохранённый статус; несовпадение пользователя, типа, территории или суммы даёт HTTP 409.

Внутри D1 batch выполняются регистрация операции, условное списание, условное зачисление и перевод записи в completed/rejected. Зачисление зависит от успешного списания через changes()=1. Это не позволяет повторному batch с уже занятым operationId повторно провести перевод. Недостаток средств приводит к rejected, а не к отрицательному балансу.

Клиент App.jsx формирует отдельный ключ для комбинации пользователя, типа действия и территории. Ключ хранится в localStorage, при недоступности — в sessionStorage, а затем поддерживается в памяти текущего приложения. Пока запрос не подтверждён, изменение суммы для той же операции и территории блокируется. После однозначного ответа ключ удаляется. Это защищает в том числе от повторной отправки после потери сетевого ответа, пока сохранённый ключ доступен клиенту.

11.8. Покупка визуалов и журнал расхода

POST /api/customization/purchase поддерживает два источника оплаты:
- личный баланс user_currency с записью предмета в user_items;
- казна территории city_treasury с записью предмета в city_items.

Для покупки проверяются авторизация, активность предмета, цена, ограничения government_marker и hidden_from_users, а также наличие предмета в соответствующем инвентаре. Скрытые предметы доступны для покупки только главному инспектору. При оплате из казны покупатель должен иметь соответствующую территорию в списке управляемых им городов.

Списание и выдача предмета объединены в D1 batch. UPDATE уменьшает баланс только при достаточном остатке и отсутствии предмета в инвентаре; следующий INSERT выдаёт предмет только если предыдущее изменение действительно состоялось. Повторная или параллельная покупка не должна списать стоимость второй раз.

После покупки стоимость положительной покупки дополнительно записывается в gem_spend_log с территориальной атрибуцией. Для личной покупки территория выбирается среди управляемых городов пользователя либо среди территорий его членства; при покупке из казны используется оплаченная территория. Этот журнал нужен, в частности, для критерия достижения «потрачено самоцветов». Само списание и запись gem_spend_log не входят в один D1 batch — последствия этого разделены в finding 30.17.

11.9. Условия и выдача достижений

Достижения представлены активными customization_items с achievement_enabled=1. Для одного предмета можно задать один или несколько порогов:
- число жителей;
- сумма самоцветов, учтённых в gem_spend_log;
- средняя оценка инспектора;
- средняя оценка игроков;
- число одобренных скриншотов;
- число комментариев;
- число активных визуалов в инвентаре территории.

Если задано несколько условий, должны выполняться все заданные пороги. Если не задано ни одного условия, достижение не считается выполненным.

Проверка проводится только для одобренной территории, у которой есть owner_telegram_id. Число жителей считается как объединение уникальных Telegram ID из city_memberships, territory_managers и владельца территории. Визуалы считаются по уникальным активным предметам в city_items; личные предметы жителей в этот показатель не входят.

При выполнении условия предмет добавляется в city_items с source='achievement', а факт выдачи фиксируется в achievement_awards. Первичный ключ (territory_id,item_id) не позволяет выдать одно и то же достижение повторно. Проверка выполняется проходами: награда, добавленная как визуал, может увеличить показатель visuals и открыть следующее достижение в рамках того же запуска.

Автоматическая оценка вызывается после покупки визуала. POST /api/achievements/recheck доступен только главному инспектору и последовательно перепроверяет все одобренные территории. Ответ содержит checked, skipped, awarded и errors. Награда за достижение — визуальный предмет; отдельного начисления самоцветов эта функция не выполняет.

12. ПЕРСОНАЛЬНЫЕ И ГЛОБАЛЬНЫЕ НАСТРОЙКИ
======================================================================

12.1. Персональные настройки

Маршруты:
- GET /api/user-settings
- POST /api/user-settings

Хранятся:
- тема;
- часовой пояс;
- масштаб карты;
- настройки уведомлений о событиях;
- индивидуальные настройки уведомлений по территориям.

Основная таблица:
user_preferences

Таблица территориальных уведомлений:
territory_notification_preferences

Текущая тема, доступная в коде:
vox

Часовой пояс по умолчанию:
UTC+3

Масштаб карты по умолчанию:
88%

Диапазон ползунка:
1–100%.

Преобразование процента в реальный масштаб экспоненциальное:
100% = 1x;
1% = 24x.

Формула:
scale = 24 ^ ((100 - percent) / 99)

Таким образом, равные шаги ползунка дают одинаковое относительное изменение масштаба. Значение 88% соответствует приблизительно 1.46x.

12.2. Уведомления

Поддерживаются уведомления о событиях и индивидуальные настройки уведомлений по территориям.

Для территориальных уведомлений:
- если у пользователя есть явная запись в territory_notification_preferences, используется она;
- если записи нет, управляющий территории получает уведомления по умолчанию;
- обычный житель без явной настройки не получает такие уведомления по умолчанию.

Старый общий переключатель уведомлений сохранён для совместимости с предыдущими версиями клиента, но больше не управляет отдельным глобальным режимом уведомлений.

12.3. Глобальные настройки

Маршруты:
- GET /api/admin/global-settings
- POST /api/admin/global-settings

Доступны только главному инспектору.

Поддерживаются отдельные ключи:
- map_zoom — глобальный масштаб карты;
- theme — глобальная тема.

Таблица:
global_setting_overrides

Каждый параметр хранит:
- значение;
- время окончания действия или NULL для постоянного значения;
- время обновления;
- ID главного инспектора, изменившего настройку.

Масштаб и тема применяются и снимаются независимо. Для каждого параметра можно установить срок действия или включить постоянный режим. Допустимый срок — до 10 лет.

Глобальное значение является временным значением по умолчанию/переопределением, а не безусловной блокировкой пользовательского выбора.

Если пользователь меняет конкретный параметр во время действия глобального значения, backend записывает отдельную отметку для этого параметра и пользователь продолжает использовать собственное значение. Второй параметр при этом не затрагивается.

После окончания срока глобального значения пользователь возвращается к своему личному значению, если не сделал собственный выбор во время действия соответствующего глобального режима.

Отметка пользовательского выбора привязана к версии конкретного глобального изменения через updated_at. При создании нового глобального изменения с новым updated_at новое значение может снова примениться к пользователю.

13. ИНТЕРАКТИВНАЯ КАРТА: ГЕОМЕТРИЯ И ОТОБРАЖЕНИЕ
======================================================================

13.1. Компонент карты

Основной React-компонент:
VoxMap

Расположен в:
src/App.jsx

Карта отображается во вкладке «Карта» раздела «Территории».

Внешняя область карты квадратная. Изображение карты служит базовым слоем, поверх него размещаются детальные тайлы и маркеры территорий.

13.2. Координатная система мира

Текущая геометрия определяется в:
shared/world-map-coordinates.js

Тип:
minecraft-world-block-centers

Границы:
minX = -3008
maxX = 3007
minZ = -3008
maxZ = 3007

Количество координатных позиций по каждой оси:
6016

Геометрия фиксирована и не зависит от пиксельного разрешения изображения карты.

Координаты переводятся в проценты с учётом центров блоков:
xPercent = ((x - minX + 0.5) / worldWidth) × 100
yPercent = ((z - minZ + 0.5) / worldHeight) × 100

Невалидные координаты не переводятся в положение маркера.

Старые manifest без coordinateSystem остаются совместимыми. Если manifest содержит координатную систему, клиент проверяет её соответствие текущим границам.

13.3. Маркеры территорий

Маркеры отображаются отдельным слоем над картой.

Для территории используются её координаты X/Z. Размер маркера визуально компенсирует увеличение карты обратным коэффициентом:
1 / scale

Это не позволяет значкам чрезмерно увеличиваться вместе с картой.

Могут использоваться:
- выбранный визуальный предмет-маркер;
- стандартный маркер, если пользовательский не задан.

Для государственных территорий применяется совместимый тип государственного маркера.

Маркер открывает страницу соответствующей территории. Слой маркеров включается после готовности необходимых данных.

13.4. Загрузка карты в клиенте

При открытии вкладки карты вызывается loadWorldMap().

Сначала выполняется:
GET https://voxygen-map-assets.counterboard.workers.dev/world-map/manifest.json

К запросу добавляется параметр check с текущим временем, используется cache: no-store.

Проверяется:
- наличие mapVersion;
- наличие source;
- поддерживаемый source.type;
- размеры источника Deep Zoom;
- совместимость coordinateSystem;
- наличие previewUrl.

Поддерживаемые клиентские типы:
- deepzoom;
- url-grid.

Если manifest корректен, клиент загружает preview, декодирует его и устанавливает как базовое изображение. Затем VoxMap использует параметры источника для подгрузки тайлов.

13.5. Резервный путь

Резервная выдача цельного изображения используется только в случае HTTP 404 для manifest.

В этом случае клиент:
1. отправляет HEAD на /api/map;
2. проверяет Content-Type и X-Map-Version;
3. загружает изображение GET-запросом с параметром версии.

Если manifest существует, но он некорректен или недоступен с другой ошибкой, клиент не должен обходить его через старый путь. Это предотвращает незаметное использование устаревшей карты при проблемах новой публикации.

Резервный путь выдаёт целое изображение, а не Deep Zoom-тайлы.

14. ЗАГРУЗКА ИСХОДНОЙ КАРТЫ

14.1. Интерфейс

Загрузка доступна главному инспектору в административной панели профиля, в разделе карты мира.

Поддерживаемые форматы:
- PNG;
- JPG/JPEG;
- WebP.

Максимальный размер:
90 000 000 байт (90 МБ).

Клиент проверяет файл и считывает его реальные растровые размеры. Передача исходника выполняется без предварительного уменьшения изображения фронтендом.

14.2. HTTP-запрос

POST https://voxygen.counterboard.workers.dev/api/map

Заголовки:
- Content-Type — MIME-тип исходного изображения;
- X-Telegram-Init-Data — Telegram Init Data;
- X-Map-Size — размер исходного файла в байтах.

Для передачи используется XMLHttpRequest с отображением прогресса загрузки. Клиент обрабатывает ошибки соединения, прерывание и превышение времени ожидания.

14.3. Серверная проверка

saveMapSettings() сначала вызывает requireMainInspector().

Затем проверяет:
- разрешённый MIME-тип;
- заявленный размер;
- совпадение с Content-Length, если он доступен;
- ограничение 90 МБ;
- наличие тела запроса;
- наличие GitHub и pipeline конфигурации.

Для потоковой передачи используется FixedLengthStream. Это позволяет пересылать большой файл в GitHub без необходимости целиком собирать его в памяти Worker и одновременно контролировать длину потока.

14.4. Секреты и переменные основного Worker

Используемые secrets:
- BOT_TOKEN — Telegram Bot API и проверка Init Data;
- INSPECTOR_CHAT_ID — ID или username главного инспектора;
- GITHUB_TOKEN — загрузка исходного изображения в Release;
- MAP_PIPELINE_GITHUB_TOKEN — запуск workflow обработки карты;
- BANKER_TELEGRAM_ID — отдельный Telegram ID банковского пользователя.

Обычные переменные:
- GITHUB_OWNER = CounterBoard;
- GITHUB_REPO = Voxygen-map-storage;
- GITHUB_RELEASE_TAG = world-map.

D1 binding:
DB → база voxygen.

Значения секретов в документации намеренно не приводятся.

16. АВТОМАТИЧЕСКАЯ ОБРАБОТКА DEEP ZOOM
======================================================================

16.1. Workflow

Репозиторий:
CounterBoard/Voxygen-map-assets

Workflow:
.github/workflows/publish-map.yml

Название:
Process and publish world map

Триггер:
workflow_dispatch

Передаваемые inputs:
- image_url;
- map_version.

Worker вызывает GitHub API:
POST /repos/CounterBoard/Voxygen-map-assets/actions/workflows/publish-map.yml/dispatches

ref:
main

Успешный запуск workflow ожидает HTTP 204.

16.2. Параметры GitHub Actions

- Ubuntu latest;
- Python 3.12;
- Pillow и Requests;
- Node.js 22;
- Wrangler latest;
- timeout job: 30 минут;
- concurrency group: world-map-publish;
- cancel-in-progress: false.

Параллельный запуск не отменяет автоматически уже выполняющуюся обработку.

16.3. Проверка исходного URL

Workflow принимает только HTTPS URL с доменом github.com и путём, начинающимся с:
 /CounterBoard/Voxygen-map-storage/releases/download/

Это не позволяет подставить произвольный внешний URL.

Загрузка исходника выполняется потоково блоками по 1 МБ.

Если репозиторий с исходником приватный, может использоваться MAP_SOURCE_GITHUB_TOKEN. Для публичного репозитория он не обязателен.

При перенаправлении на отдельный адрес скачивания GitHub токен не передаётся на этот адрес.

16.4. Скрипт генерации

Файл:
tools/build_map.py

Библиотека:
Pillow

Параметры:
- TILE_SIZE = 512;
- PREVIEW_MAX = 1200;
- MAX_RASTER_DIMENSION = 30000.

Текущий генератор принимает квадратную карту. Это требование сохраняет одинаковый масштаб игрового пространства по осям X и Z.

Размер каждой стороны должен быть не меньше 1 пикселя и не больше 30 000 пикселей. Минимум 512 пикселей в актуальном коде не установлен.

16.5. Подготовка изображения

Генератор:
1. открывает исходное изображение;
2. корректирует ориентацию через EXIF;
3. преобразует изображение в RGBA;
4. получает ширину и высоту;
5. проверяет размер и квадратность.

16.6. Превью

Копия исходника уменьшается так, чтобы стороны не превышали 1200 пикселей.

Используется LANCZOS.

Результат:
preview.webp

Изображение сохраняется в WebP lossless, method=6.

16.7. Пирамида уровней

Максимальный уровень:
maxLevel = ceil(log2(max(width, height)))

Создаются уровни от 0 до maxLevel включительно.

Для уровня:
scale = 2^(maxLevel - level)

Размер каждой стороны рассчитывается с округлением вверх. На максимальном уровне используется исходное разрешение.

Каждый уровень формируется из исходного RGBA-изображения с использованием LANCZOS.

16.8. Разделение на тайлы

Размер тайла:
512 × 512 px

Число столбцов:
ceil(levelWidth / 512)

Число строк:
ceil(levelHeight / 512)

Крайние тайлы справа и снизу могут быть меньше 512 пикселей.

Каждый тайл сохраняется в WebP lossless с method=6.

Путь:
public/world-map/versions/<mapVersion>/tiles/<level>/<x>_<y>.webp

Пример:
public/world-map/versions/map-example/tiles/13/0_0.webp

16.9. Координатная система в manifest

Генератор записывает в manifest:
type = minecraft-world-block-centers
minX = -3008
maxX = 3007
minZ = -3008
maxZ = 3007

Эти значения должны соответствовать shared/world-map-coordinates.js основного репозитория.

19. ДИНАМИЧЕСКАЯ ЗАГРУЗКА DEEP ZOOM В БРАУЗЕРЕ
======================================================================

19.1. Принцип

Клиент не загружает все тайлы сразу. Он вычисляет, какая область карты сейчас видна, и запрашивает только тайлы, которые пересекают эту область, с небольшим запасом.

Превью показывается первым и служит базовым изображением. Детальные тайлы накладываются поверх него по мере загрузки.

19.2. Выбор уровня детализации

Используются:
- размеры исходной карты;
- tileSize;
- текущий scale;
- размеры viewport;
- devicePixelRatio;
- minLevel и maxLevel из manifest.

В текущем клиентском коде:
targetPixels = max(viewportWidth, viewportHeight) × devicePixelRatio × scale

idealLevel = maxLevel + log2(targetPixels / max(mapWidth, mapHeight))

Выбранный уровень:
ceil(idealLevel), ограниченный диапазоном minLevel ... maxLevel.

Для devicePixelRatio применяется ограничение сверху 3.

19.3. Вычисление видимых тайлов

Функция:
buildVisibleTiles()

Переводит границы видимой области viewport в нормализованные координаты карты.

Затем вычисляет:
- начальный и конечный X тайлов;
- начальный и конечный Y тайлов;
- URL каждого тайла;
- его положение и размеры на карте.

Добавляется запас примерно в один тайл вокруг видимой области.

19.4. Обновление

Функция:
scheduleTileRefresh()

Откладывает пересчёт примерно на 110 мс после изменений положения/масштаба.

tileSignatureRef хранит подпись списка тайлов. Если список не изменился, лишнее обновление React не выполняется.

В текущей реализации отдельного AbortController для отмены каждого уже начатого HTTP-запроса тайла нет. При смене набора React обновляет набор отображаемых изображений; уже начатая загрузка отдельного изображения может завершиться на уровне браузера.

19.5. Отображение

Тайлы размещаются абсолютными HTML image-элементами внутри слоя карты.

Для изображений используется асинхронное декодирование и высокий приоритет загрузки. Тайлы не перехватывают пользовательские указатели.

Положение и размеры рассчитываются относительно исходного изображения и задаются в процентах.

20. УПРАВЛЕНИЕ КАРТОЙ И МАСШТАБ
======================================================================

20.1. Перемещение

Используются Pointer Events:
- один указатель перемещает карту;
- два указателя запускают pinch-жест.

Трансформация хранится в transformRef.

20.2. Pinch-to-zoom

Для двух указателей вычисляются:
- расстояние между пальцами;
- середина жеста;
- исходный масштаб;
- положение точки карты под серединой жеста.

Отношение нового расстояния к исходному задаёт новый масштаб. Пересчёт смещения сохраняет точку под пальцами.

20.3. Колесо мыши

Поддерживается масштабирование колесом мыши. Изменение масштаба зависит от величины прокрутки и выполняется экспоненциально.

20.4. Ограничения

Реальный масштаб слоя:
1 ≤ scale ≤ 24.

Функции bounds() и clamp() ограничивают смещение так, чтобы карту нельзя было бесконечно увести за пределы viewport.

При scale=1 смещение по X/Y ограничено нулём. При увеличении допустимые границы растут пропорционально масштабу.

20.5. Перерисовка

Трансформация применяется к существующему DOM-слою:
translate(x, y) scale(scale)

Для обновления используется requestAnimationFrame. Это уменьшает количество React-render при движении карты и помогает сохранить чёткость отображения.

Размер маркеров компенсируется через CSS-переменную:
--vox-marker-inverse-scale = 1 / scale

20.6. Пользовательский масштаб

Персональный масштаб задаётся ползунком 1–100%.

Преобразование:
scale = 24 ^ ((100 - percent) / 99)

100% означает исходный масштаб 1x; 1% — максимальное увеличение 24x.

Начальное значение для новых пользовательских настроек:
88%.

Изменение масштаба не меняет диапазон детализации Deep Zoom напрямую: клиент пересчитывает требуемый уровень в зависимости от фактического масштаба карты и плотности экрана.

======================================================================
21. ОБНОВЛЕНИЕ ОПУБЛИКОВАННОЙ КАРТЫ
======================================================================

После загрузки исходника Worker возвращает mapVersion.

Клиент начинает опрашивать manifest:
GET /world-map/manifest.json?check=<timestamp>

Интервал:
5 секунд.

Предельное ожидание в интерфейсе:
25 минут.

Workflow GitHub Actions имеет timeout:
30 минут.

Клиент ждёт, пока manifest.mapVersion совпадёт с ожидаемой версией. После этого:
1. получает previewUrl;
2. загружает и декодирует превью;
3. формирует новый источник карты;
4. устанавливает новую версию;
5. сообщает об обновлении карты.

Пока новая публикация не завершена, предыдущий manifest остаётся доступен. Новая карта считается опубликованной только после успешного обновления статических ресурсов.

Если публикация не завершилась за 25 минут, интерфейс сообщает о проблеме и предлагает проверить workflow.

22. РЕЗЕРВНАЯ ВЫДАЧА ИСХОДНОГО ИЗОБРАЖЕНИЯ
======================================================================

Маршруты:
- HEAD /api/map
- GET /api/map

Backend-функция:
getMapSettings()

D1:
- world_map_github_url;
- world_map_github_content_type.

Worker кэширует настройки ссылки на 30 секунд в памяти экземпляра.

Если ссылка отсутствует:
- HEAD возвращает 404;
- GET возвращает MAP_NOT_UPLOADED.

Если ссылка есть, Worker получает изображение из GitHub Releases и передаёт его клиенту.

Если GitHub возвращает ошибку, Worker повторно читает актуальную ссылку из D1 и пробует получить файл ещё раз. Это помогает, если экземпляр Worker временно использует старый URL.

Ответ содержит соответствующий Content-Type, X-Map-Version, X-Content-Type-Options и cache headers. При доступности upstream также могут передаваться Content-Length и ETag.

Резервный режим не использует Deep Zoom и передаёт целое изображение. Это совместимый путь на случай отсутствия manifest, но не основной способ работы карты.

- POST /api/customization/items, POST /api/customization/items/visibility, POST /api/customization/items/reorder, POST /api/customization/tags/reorder, PATCH/DELETE /api/customization/items/{id} → операции каталога — requireMainInspector().

Смешанные и специальные правила:
- POST /api/territories → createTerritory() — проверяет Telegram Init Data; обычному пользователю нужен verified-профиль, главный инспектор может создать одобренную территорию напрямую.
- POST/PATCH/DELETE /api/events → createEvent()/updateEvent()/deleteEvent() — requireUser() и проверки автора события, территории и полномочий; GET с manage=1 отдельно ограничен главным инспектором.
- POST /api/admin/territories/rename → renameTerritory() — requireUser() и isTerritoryManager(); несмотря на сегмент admin в URL, не ограничен исключительно главным инспектором.
- POST /api/screenshots/{id} → moderateScreenshot() — маршрут присутствует, но вызов не передаёт обязательный аргумент approve; HTTP-одобрение не работает, см. 30.5.
- POST /api/webhook → webhook() — отдельной проверки пользовательской авторизации нет; подлинность Telegram update должна подтверждаться webhook secret, проверка которого в текущем Worker не обнаружена, см. 30.2.



24.2. Маршруты без прямого вызова из текущего App.jsx

При статической сверке строковых API-вызовов в src/App.jsx не найдено прямого обращения к следующим серверным операциям:
- POST /api/territories/claim-owner;
- GET/POST /api/vox-grid и POST /api/vox-grid/reset;
- POST /api/treasury/withdraw;
- POST /api/screenshots/{id} для HTTP-модерации;
- GET /api/recruitment — обработчик getRecruitment отсутствует, а App.jsx использует данные recruitment из /api/territories.

Это не доказывает, что маршруты не используются вообще: их могут вызывать внешние клиенты, старые версии приложения или другие процессы. До отдельной проверки потребителей их не следует удалять. Для claim-owner и HTTP-модерации при этом сохраняются замечания безопасности и корректности из раздела 30.



24.3. Семантика GET-запросов и побочные эффекты

Не все GET-маршруты являются строго read-only. В Worker часть чтений совмещена с ленивой инициализацией схемы, созданием отсутствующих записей и очисткой устаревших данных. Это важно при анализе повторных запросов и диагностике D1.

Подтверждённые примеры:
- GET /api/territories → getTerritories(): вызывает ensureRecruitmentTable() и ensureWorldTables(). Эти функции могут создавать/обновлять структуру D1 при первом обращении или после обновления версии схемы. В обычном режиме обработчик выполняет чтение связанных таблиц; необязательные компоненты при ошибках попадают в degradedAreas.
- GET /api/vox-grid → getVoxGrid(): вызывает ensureWorldTables(), поэтому публичное чтение сетки также может запустить инициализацию/миграции D1.
- GET /api/faq → getFaq(): вызывает ensureMapSettingsTable(); публичное чтение FAQ может создать таблицу app_settings.
- GET /api/home-feature-button → getHomeFeatureButton(): требует requireUser(), вызывает ensureWorldTables() и ensureMapSettingsTable(); помимо авторизации может выполнять инициализацию таблиц.
- GET /api/user-settings → getUserSettings(): вызывает инициализацию таблиц настроек и INSERT OR IGNORE для user_preferences. Для нового пользователя создаётся строка со значениями по умолчанию: тема vox, часовой пояс UTC+3, уведомления событий выключены, масштаб карты 88%.
- GET /api/treasury → getTreasury(): после проверки авторизации и членства/управления создаёт отсутствующие строки city_treasury и user_currency с нулевым балансом.
- GET /api/customization → getCustomization(): требует авторизацию, инициализирует world tables и создаёт отсутствующую строку user_currency. Обычный (не lite=1) ответ дополнительно вызывает cleanupCustomizationCategories(): удаляет категории без активных предметов и уплотняет sort_order. При выборе казны управляющего может создать отсутствующую строку city_treasury.
- GET /api/events → getEvents(): инициализирует таблицы событий и вызывает purgeExpiredEvents(). Удаляются события, завершившиеся более 24 часов назад, их напоминания, а также ключи идемпотентности создания событий старше 30 дней.
- GET/HEAD /api/map → getMapSettings(): вызывает cleanupLegacyMapStorage(), который инициализирует app_settings и удаляет устаревшие ключи world_map_object_key, vox_map_image и jorick_map_image. Очистка кешируется на уровне экземпляра Worker.

Таким образом, слово GET описывает HTTP-метод, но само по себе не гарантирует отсутствие изменений в D1. Из явно read-only маршрутов особенно выделяется GET /api/admin/diagnostics/d1: он намеренно не вызывает ensureWorldTables() и не запускает миграции или очистку.

24.4. Ключевые контракты данных между App.jsx и Worker

- Список карты: App.jsx запрашивает GET /api/territories?view=summary и принимает объект {ok, territories, degradedAreas}; Worker возвращает именно этот объект. В summary режиме residents, managers, reviews и screenshots не загружаются полностью, чтобы сократить ответ; для выбранной территории App.jsx отдельно запрашивает GET /api/territories?detail={id}.
- Детальная территория: detail-запрос возвращает массив territories с расширенными полями reviews, screenshots, residents, resident_rows, resident_telegram_ids, managers и manager_telegram_ids. App.jsx переносит эти поля в текущую запись территории.
- Профильная кастомизация: GET /api/customization?scope=profile&territoryId=... допускает просмотр для управляющего или участника. Ответ содержит cityInventory и экипированные marker/background ID. Поле cityRole в текущем Worker выставляется в 'manager' при любом допустимом profileTerritoryId, в том числе если запросивший только участник; текущий App.jsx cityRole не использует.
- Набор: App.jsx сохраняет настройки через POST /api/recruitment с territoryId, description, enabled и recruitmentUsername. Worker проверяет право управляющего, сохраняет описание/флаг и нормализует контакт к одному из управляющих. Передаваемый клиентом ownerNickname обработчиком не используется.
- Казна: POST /api/treasury/deposit и POST /api/treasury/donate передают operationId, territoryId и amount. Worker применяет идемпотентный финансовый перевод; повтор запроса с тем же operationId не должен повторно списывать/зачислять средства. Ответы используют snake_case personal_balance; депозит также возвращает balance, isManager и replayed.
- Ивенты: POST /api/events передаёт requestKey и поля события; Worker связывает ключ с Telegram ID и SHA-256 отпечатком payload. Повтор того же ключа с тем же содержимым возвращает ранее созданный id, а повтор с изменённым содержимым отклоняется HTTP 409. GET /api/events возвращает events, а вложенное reminder формируется из записи event_reminders.
- Настройки: GET /api/user-settings возвращает settings с timezone, mapZoomPercent, personalMapZoomPercent, globalOverrides и параметрами уведомлений. POST /api/user-settings сохраняет настройки и возвращает повторно сформированный объект settings.
- Ошибки: App.jsx централизованно переводит ряд HTTP-статусов и технических сообщений в пользовательские тексты через apiErrorMessage()/safeCaughtError(). parseApiResponse() дополнительно требует успешный HTTP-статус и JSON с ok не равным false.

Примечание: это описание фактического контракта текущих исходников, а не гарантия совместимости со старыми внешними клиентами.

25. СТРУКТУРА И НАЗНАЧЕНИЕ ОСНОВНЫХ ТАБЛИЦ D1
======================================================================

Базовая схема находится в bot/schema.sql. Worker выполняет дополнительные CREATE TABLE и ALTER TABLE при инициализации и обновлении схемы. Поэтому schema.sql не является полным перечнем всех фактических таблиц.

Основные таблицы:

Пользователи и идентичность:
- users — Telegram ID, Telegram username, Minecraft nickname, статус и игровые идентификаторы;
- user_directory — вспомогательный каталог пользователей;
- pre_registered_users — предварительно зарегистрированные связки username и Minecraft-ника;
- inspectors — список инспекторов;
- user_preferences — персональные настройки;
- territory_notification_preferences — индивидуальные настройки уведомлений по территориям.

Территории и управление:
- territories — основные сведения о территориях, координаты, статус, владелец и показатели;
- territory_managers — дополнительные управляющие;
- city_memberships — членство пользователей в территориях;
- city_invites — приглашения;
- manager_change_requests — запросы на изменение управляющих;
- manager_change_votes — голоса по таким запросам;
- territory_approval_sessions — пошаговые сессии утверждения территории;
- recruitment — объявления о наборе.

Рейтинги, отзывы и изображения:
- ratings — оценки пользователей;
- inspector_ratings — оценки инспекторов;
- comments — комментарии;
- comment_replies — ответы;
- screenshots — отправленные скриншоты и их модерация.

Кастомизация и экономика:
- customization_categories — категории визуальных предметов;
- customization_items — предметы;
- user_currency — личные балансы;
- city_treasury — балансы казны;
- financial_operations — идемпотентные финансовые операции;
- user_items — приобретённые пользователями предметы;
- city_items — предметы, связанные с территориями;
- city_customization — выбранное оформление города;
- achievement_awards — выданные награды;
- gem_spend_log — журнал операций расходования самоцветов.

События и уведомления:
- events — события;
- event_reminders — напоминания;
- event_create_requests — защита от повторного создания события.

Прочие подсистемы:
- app_settings — настройки приложения, включая ссылку на исходную карту;
- global_setting_overrides — глобальные переопределения настроек;
- vox_grid — состояние ячеек VOX Grid;
- bank_transactions — обработанные Telegram-банковские операции;
- voxygen_schema_meta — версии схем и миграций.

Важное свойство схемы:
Worker выполняет ленивые миграции. Таблицы и колонки могут создаваться/добавляться при первом обращении к соответствующей подсистеме. Версии миграций в текущем исходном коде:
- WORLD_SCHEMA_VERSION = 2026-11-v27;
- RECRUITMENT_SCHEMA_VERSION = 2026-10-v25.

Ограничения воспроизводимости схемы:
- bot/schema.sql не содержит territories.owner_telegram_id и territories.owner_telegram_username; в текущем initializeWorldTables() также не обнаружено добавление этих двух колонок, хотя backend активно их использует.
- Таблица inspectors используется для ролей и администрирования, но её CREATE TABLE не найден ни в schema.sql, ни в Worker. Её создание является внешней предпосылкой текущего кода.
- city_memberships_multi — временная staging-таблица миграции к составному ключу city_memberships, а не постоянная таблица приложения.
- deleted_territories упоминается диагностикой как необязательная архивная таблица, но текущий Worker её не создаёт и не записывает туда удалённые территории.

Эти расхождения означают, что чистое развёртывание только по schema.sql и текущему Worker не гарантирует получения полной схемы, ожидаемой backend. Production D1 отдельно не проверялась.

27. ДИАГНОСТИКА И ОБРАБОТКА ОШИБОК
======================================================================

27.1. API

Основной Worker возвращает JSON-ответы с ok и описанием ошибки. Типичные статусы:
- 400 — некорректные данные;
- 401 — пользователь не авторизован;
- 403 — недостаточно прав;
- 404 — ресурс не найден;
- 409 — конфликт/операция ещё обрабатывается;
- 413 — слишком большой файл;
- 415 — неподдерживаемый тип файла;
- 429 — ограничение частоты;
- 500/502/503 — внутренняя или внешняя ошибка.

27.2. Request ID

Для каждого запроса основной Worker создаёт requestId и возвращает его в заголовке:
X-Request-ID

В Server-Timing добавляется время работы Worker. При ошибках формируются структурированные диагностические логи с маршрутом, методом, статусом и requestId.

27.3. Диагностика D1

Маршрут:
GET /api/admin/diagnostics/d1

Предназначен для административной диагностики базы. Доступ ограничивается серверной проверкой прав. Обработчик read-only: проверяет таблицы, количества записей, статусы, часть осиротевших связей, внешние ключи и объёмы крупных полей, не изменяя данные.

Текущий список проверок территориальных связей не включает events и territory_notification_preferences. Поддержка retainedArchivedHistory зависит от наличия deleted_territories; Worker не создаёт и не заполняет эту архивную таблицу. См. раздел 30.

27.4. Карта

Загрузка карты пишет структурированные события диагностики с этапом процесса:
- авторизация;
- очистка устаревших настроек;
- проверка файла;
- поиск Release;
- загрузка Asset;
- запуск pipeline;
- обработка результата.

Секретные значения и токены не должны попадать в логи.

28. ОГРАНИЧЕНИЯ И ВАЖНЫЕ ТЕХНИЧЕСКИЕ ОСОБЕННОСТИ
======================================================================

1. Frontend не является источником истины для прав. Все критические проверки выполняются backend.

2. Telegram ID — основной идентификатор аккаунта. Username может меняться и используется как контакт/поисковый атрибут.

3. D1 содержит постоянные данные приложения, но не содержит Deep Zoom-тайлы.

4. Исходная карта хранится в GitHub Release Asset. Ссылка и MIME-тип находятся в app_settings.

5. Публикация новой карты асинхронная. Успешная загрузка исходника ещё не означает, что новая версия уже доступна в клиенте.

6. Версионные URL тайлов позволяют использовать длительное immutable-кэширование.

7. Manifest не кэшируется, чтобы клиент мог обнаружить новую версию.

8. Текущий генератор карты требует квадратный исходник и использует фиксированную геометрию игрового мира.

9. url-grid предусмотрен в контракте, но фактически текущий pipeline публикует Deep Zoom; массив 12×12 ссылок пуст.

10. Legacy fallback /api/map используется клиентом при отсутствии manifest (404), а не при любом сбое manifest.

11. Worker выполняет миграции D1. Ручное изменение таблиц без учёта миграций может привести к несовместимости.

12. Тема в текущем backend ограничена значением vox. Поддержка других тем в UI/данных пока не подтверждена.

13. Общий старый флаг уведомлений сохранён ради совместимости, но актуальные настройки уведомлений разделены по событиям и территориям.

14. В текущей реализации загрузчик Deep Zoom обновляет список отображаемых тайлов по viewport. Отдельной принудительной отмены каждого уже начатого запроса изображения не реализовано.

30.2. Подлинность Telegram webhook

POST /api/webhook принимает JSON и обрабатывает callback_query.from.id и message.from.id. В текущем Worker не обнаружена проверка заголовка X-Telegram-Bot-Api-Secret-Token, secret_token или другого webhook-секрета.

Ролевая проверка административных callback и проверка BANKER_TELEGRAM_ID опираются на from.id из входящего JSON. Если endpoint доступен извне без дополнительной инфраструктурной защиты, поддельный update потенциально может имитировать главного инспектора, инспектора или банковского пользователя. Это особенно существенно для банковских операций и административных callback.

Функция withCors() также выставляет Access-Control-Allow-Origin: *, но CORS не является механизмом авторизации и не защищает endpoint от прямых HTTP-запросов. Внешние ограничения Cloudflare, firewall или настройки маршрута не проверялись. Поэтому вывод относится к отсутствию проверки внутри Worker и не доказывает факт эксплуатации.

Рекомендация: настроить webhook secret_token в Telegram и обязательно проверять X-Telegram-Bot-Api-Secret-Token на входе Worker до разбора update. Проверка должна предшествовать синхронизации пользователя, обработке callback и банковским операциям.

30.3. Срок действия Telegram Init Data

verifyInitData() проверяет HMAC-SHA-256 и наличие user, но не проверяет auth_date. Корректно подписанные данные не отклоняются Worker только из-за возраста.

Рекомендация: ввести явное допустимое окно времени для auth_date и отклонять слишком старые и находящиеся в будущем значения с учётом небольшого допустимого clock skew. Передачу initData через query string желательно исключить из штатного контракта, чтобы не помещать авторизационные данные в URL и потенциальные журналы запросов.

30.4. Неполная проверка владельца территории

POST /api/territories/claim-owner требует обычную Telegram-авторизацию, но не требует подтверждённого Minecraft-профиля и не сверяет пользователя с territories.owner_input. Если у одобренной территории owner_telegram_id ещё не установлен, авторизованный пользователь потенциально может назначить владельцем себя.

Текущий App.jsx не содержит прямого вызова этого маршрута, однако backend endpoint присутствует. ID территорий при этом возвращаются публичным GET /api/territories и не являются секретом. Кроме того, updateTerritoryManager() позволяет главному инспектору удалить последнего управляющего: в таком случае owner_telegram_id и owner_telegram_username могут быть сброшены в NULL. Аналогичное состояние создаёт removeManagedUserRelations(), вызываемая при удалении профиля через deleteManagedUser(): если не найден другой подтверждённый управляющий, функция также обнуляет owner_telegram_id и owner_telegram_username, сохраняя owner_input. Это создаёт состояние, в котором описанный claim-owner маршрут становится доступен для чужого присвоения.

Рекомендация: определить и реализовать проверяемое правило claim — например, сопоставление с заявленным owner_input и подтверждённым профилем. Не считать наличие только Telegram initData достаточным основанием для получения прав владельца.

30.5. Ошибка HTTP-модерации скриншотов

moderateScreenshot(request, env, screenshotId, approve) ожидает четвёртый аргумент approve. Маршрутизатор POST /api/screenshots/{id} передаёт только request, env и screenshotId. Поэтому approve становится undefined, и HTTP-маршрут всегда выбирает rejected.

Текущий App.jsx не вызывает POST /api/screenshots/{id}; он использует POST /api/screenshots для загрузки и DELETE /api/screenshots/{id} для удаления. Штатная модерация выполняется через Telegram callback.

Дополнительные особенности Telegram-модерации:
- обработчик допускает главного инспектора, управляющего территории или пользователя, чей ID равен territories.requested_by_id;
- callback не ограничивает изменение только статусом pending, поэтому старое действие может повторно изменить статус;
- HTTP-модерация использует более узкую проверку — главный инспектор или управляющий.

30.6. Неполное удаление территории

deleteTerritory() удаляет членство, отменяет ожидающие приглашения, удаляет city_items и city_customization, затем удаляет запись territories. Не все таблицы со связью territory_id очищаются этим обработчиком, а часть из них не имеет внешнего ключа с ON DELETE CASCADE.

В частности, события events и напоминания event_reminders не удаляются и не деактивируются. getEvents() использует LEFT JOIN territories, а deliverEventReminders() не требует существования связанной территории. Поэтому после удаления территории её событие может оставаться видимым в календаре и продолжать отправлять напоминания до истечения срока. Кроме того, перечисленные операции очистки выполняются отдельными последовательными запросами, а не одной D1 batch-транзакцией; при ошибке посередине возможна частично выполненная очистка.

Рекомендация: определить политику удаления — полное каскадное удаление или архивирование. Для архивной модели нужно сохранять запись территории и связанные данные в согласованной структуре; для физического удаления — явно очищать либо деактивировать все зависимые данные и напоминания.

30.7. Ограничения схемы D1

Текущий schema.sql не содержит territories.owner_telegram_id и territories.owner_telegram_username. В initializeWorldTables() не обнаружено добавление этих колонок, хотя getTerritories() читает owner_telegram_id, а createTerritory() записывает оба поля. Поэтому чистая база, созданная только по schema.sql, не соответствует запросам backend. Кроме того, initializeWorldTables() завершает работу досрочно, если в voxygen_schema_meta уже записана текущая WORLD_SCHEMA_VERSION. Исправляющую миграцию для существующих баз нужно сопровождать изменением версии, иначе код может пропустить её выполнение.

Таблица inspectors используется getRoleByTelegramId(), listInspectors() и операциями добавления/удаления инспекторов, но её DDL в Worker и schema.sql отсутствует. Код ожидает как минимум поля telegram_id, telegram_username, added_by и created_at. При отсутствии таблицы проверки ролей обычных пользователей и операции со списком инспекторов могут завершаться SQL-ошибкой.

city_memberships_multi используется как временная staging-таблица миграции. deleted_territories является необязательной таблицей, которую Worker только проверяет диагностикой; текущий код не создаёт её и не записывает в неё удалённые территории.

Рекомендация: подготовить отдельную воспроизводимую миграцию, проверить production D1 read-only диагностикой и документировать все внешние предпосылки схемы до любых изменений рабочей базы.

30.8. GET-маршруты с побочными действиями

Некоторые GET-обработчики выполняют инициализацию или изменение данных:
- GET /api/user-settings создаёт user_preferences при первом обращении;
- GET /api/treasury создаёт нулевые записи city_treasury и user_currency;

Это следует учитывать при описании семантики GET и тестировании read-only поведения. GET /api/admin/diagnostics/d1 отдельно заявлен и реализован как read-only.

30.9. Публичная выдача идентификаторов

GET /api/territories доступен без обязательной авторизации и возвращает связанные данные владельцев, управляющих и жителей, включая Telegram ID даже в режиме view=summary; в полном режиме также возвращаются username, Minecraft-идентификаторы и данные профилей. 30.13. Отсутствующий обработчик GET /api/recruitment

В маршрутизаторе worker.js присутствует ветвь GET /api/recruitment, которая вызывает getRecruitment(env). В полном файле worker.js нет определения getRecruitment и нет импорта этой функции. Следовательно, обращение к маршруту приводит к ReferenceError и общей обработке ошибки Worker с HTTP 500.

Дополнительно выполнена сверка вызываемых имён функций в полном блоке диспетчеризации с определениями и импортами Worker: проверено 83 уникальных имени, и getRecruitment является единственным неразрешённым обработчиком в этом блоке.

Функции saveRecruitment() и setRecruitmentContact() существуют и используются для записи объявления и изменения контактного управляющего.

Текущий App.jsx не вызывает GET /api/recruitment. Он получает recruitment_description, recruitment_enabled и recruitment_contact_username в составе ответа GET /api/territories. Поэтому отсутствующий обработчик является дефектом backend endpoint, но не подтверждённой поломкой текущего пользовательского интерфейса.

Рекомендация: либо реализовать getRecruitment() с явно определённым публичным контрактом, либо удалить устаревшую ветвь маршрутизации после проверки внешних потребителей. До этого маршрут следует считать неработающим.


30.14. Побочные эффекты GET-маршрутов

В текущей реализации несколько GET-маршрутов меняют состояние D1. Это не следует автоматически считать уязвимостью: операции используются для lazy initialization и обслуживания данных. Однако API не является полностью семантически read-only.

Наиболее заметные случаи:
- GET /api/events может физически удалять просроченные события, напоминания и старые ключи идемпотентности.
- GET /api/customization может удалять пустые категории и менять их sort_order.
- GET /api/treasury и GET /api/customization могут создавать нулевые записи баланса.
- GET /api/user-settings создаёт пользовательские настройки по умолчанию.
- GET /api/territories, /api/vox-grid, /api/faq, /api/home-feature-button и GET /api/map могут запускать инициализацию/миграции или legacy cleanup.

При этом GET /api/admin/diagnostics/d1 намеренно исключает ensure-функции и заявлен как read-only. Для эксплуатационной диагностики это важное различие: обычный GET некоторых разделов может менять исследуемое состояние, а диагностический endpoint — нет.



30.15. Некорректное значение cityRole в ответе кастомизации

В getCustomization() проверка profileTerritoryId допускает два случая: пользователь является управляющим территории либо состоит в city_memberships. После этой проверки ответ формирует cityRole: profileTerritoryId ? 'manager' : null. Поэтому обычный участник, которому разрешён просмотр инвентаря территории, также получает cityRole='manager'.

Это не даёт участнику серверных полномочий: изменяющий endpoint updateCityCustomization() отдельно проверяет isTerritoryManager(). Текущий App.jsx не читает поле cityRole, поэтому прямое влияние на интерфейс не установлено. Тем не менее API-контракт семантически неверен и может ввести в заблуждение будущие или внешние клиенты.

Приоритет: низкий. Исправление должно вычислять роль отдельно, например 'manager' только при isTerritoryManager(), 'resident' при членстве и null в остальных случаях; серверные проверки доступа при этом остаются обязательными.


30.16. Негарантированное завершение Telegram-банковской операции

handleBankMessage() сначала создаёт запись bank_transactions со статусом processing и уникальным update_id. Повтор того же Telegram update останавливается на INSERT OR IGNORE и возвращает bank_duplicate. После регистрации изменение user_currency или city_treasury и обновление статуса bank_transactions выполняются отдельными D1-запросами, а не одной транзакцией/batch.

Поэтому между изменением баланса и записью итогового статуса существует окно частичного выполнения. Если Worker завершится после изменения баланса, но до установки status='success', журнал может остаться processing. Если последующий запрос завершится ошибкой, catch-блок пытается поставить status='failed', хотя предшествующее изменение баланса уже могло состояться. Повторный update_id не запускает автоматическую сверку или восстановление, а возвращает bank_duplicate.

Уникальный update_id защищает от повторного применения одного и того же Telegram update, но сам по себе не гарантирует атомарность пары «изменение баланса + итоговый статус». Перед повторной ручной отправкой такой операции требуется сверять bank_transactions и фактический баланс; интерфейс журнала/процедура автоматического восстановления в проверенном коде не обнаружены.

Приоритет: средний для целостности финансового журнала. Рекомендуется объединить изменение баланса и фиксацию итогового статуса в одну D1 batch/транзакцию либо добавить безопасную процедуру восстановления зависших processing с проверкой фактического результата. Не выполнять автоматическое повторное списание без доказуемого признака, что исходное изменение не состоялось.

30.17. Покупка визуала и отдельная запись gem_spend_log

В purchaseCustomizationItem() списание самоцветов и выдача предмета выполняются одним D1 batch. Однако после успешного batch запись о расходе в gem_spend_log выполняется отдельным запросом, а затем запускается evaluateAchievementsForTerritory().

Если после успешного списания/выдачи предмета вставка в gem_spend_log завершится ошибкой, API может вернуть ошибку уже после фактически завершённой покупки. При повторном запросе обработчик обнаружит alreadyOwned и вернёт ответ до записи расхода и повторной проверки достижений. В результате сумма покупки может навсегда отсутствовать в показателе потраченных самоцветов, а достижение, зависящее от этого показателя, не будет разблокировано этой покупкой.

Приоритет: средний для согласованности экономики и достижений. Рекомендуется включить запись gem_spend_log в тот же D1 batch, что и списание/выдачу предмета, либо предусмотреть идемпотентное восстановление журнала для уже приобретённых предметов.

30.18. Источники изменения баланса и границы автоматической экономики

В просмотренном worker.js не обнаружено отдельного пассивного начисления самоцветов по времени, за задания или непосредственно за достижение. Положительное изменение личного user_currency в проверенных путях происходит через банковское зачисление либо через перевод средств из казны при treasuryWithdraw(); переводы между личным балансом и казной не создают новые самоцветы, а перемещают их между счетами. Покупка визуалов уменьшает баланс. Достижения выдают визуальные предметы, а не валюту.

Это вывод по найденным операциям записи в текущем worker.js, а не утверждение об отсутствии внешних ручных изменений production D1 или сторонних процессов, которые не входят в проверенный код.


30.19. Отмена приглашений пользователя в других городах

В inviteResident() при создании приглашения зарегистрированному пользователю выполняется запрос:

UPDATE city_invites
SET status='cancelled', responded_at=?
WHERE target_telegram_id=? AND status='pending'

Условие не ограничено territory_id. Поэтому новое приглашение в один город отменяет все ожидающие приглашения этому Telegram-пользователю из остальных городов. Это не связано с тем, что пользователь уже состоит в другом городе: city_memberships использует составной ключ (telegram_id, territory_id), а система допускает членство в нескольких территориях.

Для приглашения по Minecraft-нику, который ещё не сопоставлен с Telegram ID, эта массовая отмена вообще не выполняется: создаётся отдельная запись с target_telegram_id=NULL. Поведение зависит от того, найден ли пользователь в users на момент приглашения.

В результате два сценария имеют разную семантику: приглашение известному пользователю отменяет все его предыдущие pending-приглашения, а приглашение по ещё не подтверждённому нику оставляет прежние приглашения активными.

Приоритет: средний для корректности пользовательского сценария. Если цель — запретить несколько одновременных приглашений одному пользователю, ограничение следует реализовать явно и согласованно с поддержкой нескольких городов. Если приглашения должны быть независимыми, UPDATE должен ограничиваться нужной территорией либо конкретной записью.


30.20. Повторная отправка ожидающих приглашений при каждом сообщении боту

Обработчик входящего Telegram message вызывает notifyPendingInvitesForUser() для отправителя до дальнейшей обработки банковских сообщений и команд главного инспектора. Функция выбирает все city_invites со status='pending' для пользователя и повторно вызывает sendResidentInvite() для каждой записи.

В таблице city_invites нет поля или отдельной записи, фиксирующей успешную отправку Telegram-сообщения, а sendResidentInvite() не обновляет статус приглашения после отправки. Поэтому каждое новое сообщение пользователя боту может повторно отправить ему все ещё ожидающие приглашения. Ошибка Telegram также только записывается в лог, а приглашение остаётся pending и будет повторно выбрано при следующем сообщении.

Для приглашения, сохранённого до подтверждения Minecraft-ника, notifyPendingInvitesForUser() сначала сопоставляет target_telegram_id по совпадающему нику. После подтверждения профиля функция начинает отправлять приглашение, но не помечает его как уже доставленное.

Приоритет: средний для качества Telegram-взаимодействия. Нужен отдельный признак отправки/идентификатор сообщения или иная идемпотентная схема уведомлений, не меняющая статус принятия приглашения.


30.21. Истечение голосования за управляющего не обслуживается фоновым процессом

При создании manager_change_requests устанавливается expires_at = now + 24 часа. Однако scheduled handler Worker выполняет только deliverEventReminders() и purgeExpiredEvents(); вызовов finalizeManagerChangeRequest() или очистки истёкших manager_change_requests в нём нет.

Завершение голосования вызывается из handleManagerVoteCallback(). Если после истечения срока никто не нажмёт старую inline-кнопку, запись продолжит иметь status='pending'. Если кто-либо нажмёт кнопку уже после срока, обработчик вызовет finalizeManagerChangeRequest(), и запрос будет отклонён либо обработан согласно накопленным голосам. Таким образом, 24 часа — это порог, проверяемый при следующем callback, а не гарантированное автоматическое завершение в момент истечения срока.

GET /api/city/management возвращает участников, приглашения, управляющих и контакт набора, но не возвращает manager_change_requests. Текущий интерфейс не получает из этого endpoint список и статус зависших голосований.

Приоритет: низкий/средний для согласованности статусов. Рекомендуется добавить фоновое завершение истёкших голосований либо явно описать callback-зависимую семантику и обеспечить доступ к текущему статусу запроса.


30.22. Статус «одобрено» может сохраниться без фактического изменения роли

finalizeManagerChangeRequest() сначала меняет manager_change_requests.status на approved, а затем отдельным запросом вызывает applyManagerChange(). Возвращаемое значение applyManagerChange() не проверяется, а изменение статуса и изменение членства/управляющих не объединены в один D1 batch.

Это создаёт подтверждённый по структуре кода сценарий рассогласования: например, запрос на повышение был создан для жителя, но до завершения голосования его членство удалили. applyManagerChange() повторно проверит наличие city_memberships и вернёт false. При этом заявка уже останется со статусом approved, а пользователь не станет управляющим. Аналогичная ситуация возможна, если необходимые условия передачи владельца при понижении уже не выполняются.

Кроме того, между чтением запроса со статусом pending и записью итогового статуса нет атомарной блокировки всего процесса. Два почти одновременных callback могут прочитать один и тот же pending-запрос до фиксации результата; UPDATE содержит условие status='pending', но число изменённых строк не проверяется перед вызовом applyManagerChange(). Это создаёт риск повторного выполнения пост-обработки при гонке.

Приоритет: средний для целостности ролей и аудита голосований. Следует атомарно фиксировать решение и изменение ролей либо проверять результат условного UPDATE и успешность applyManagerChange(); при неудаче нельзя оставлять ложный статус approved.


30.23. Передача и снятие управляющих выполняются последовательными D1-запросами

updateTerritoryManager(), updateTerritoryOwner() и applyManagerChange() изменяют owner_telegram_id, territory_managers и city_memberships несколькими отдельными запросами. Эти операции не объединены в единый D1 batch. В updateTerritoryOwner() главный инспектор сначала записывает нового владельца, затем добавляет прежнего владельца в city_memberships и очищает членство/строку управляющего у нового владельца; при ошибке между запросами возможен тот же частично обновлённый состав прав.

При смене владельца главный инспектор сначала обновляет owner_telegram_id, затем удаляет возможные старые записи членства/управления у нового владельца, удаляет прежнего владельца из territory_managers и добавляет его в city_memberships. При снятии владельца с пустым username сначала назначается следующий управляющий либо очищаются owner-поля, затем удаляется прежняя запись управляющего и добавляется членство.

При ошибке между этими запросами D1 может сохранить промежуточное состояние: например, нового owner уже записали, но прежний управляющий ещё не удалён; либо старый управляющий удалён, но его членство ещё не создано. Проверки getTerritoryManagerRows() и isTerritoryManager() объединяют владельца и записи territory_managers, поэтому некоторые промежуточные состояния могут временно давать неоднозначный состав прав.

Уведомления Telegram отправляются после отдельных изменений и не являются частью транзакции. Ошибка отправки в большинстве этих мест перехватывается, поэтому сама по себе не откатывает операцию.

Приоритет: средний для целостности управления. Перенос владельца и смену роли следует выполнять атомарным batch с заранее рассчитанными значениями и последующей проверкой состава управляющих.


30.24. Сопоставление и отправка приглашений не имеют полного механизма идемпотентности

city_invites.id является первичным ключом, а индексы idx_city_invites_target и idx_city_invites_city ускоряют выборку, но не обеспечивают уникальность активного приглашения на пару «пользователь — территория». При повторном запросе inviteResident() создаёт новый UUID и новую запись. Запрос membership считывает наличие существующего членства, однако результат переменной membership далее не используется и не блокирует создание приглашения.

При принятии приглашения обработчик проверяет существующее членство и не создаёт дубликат благодаря составному ключу city_memberships. Тем не менее повторные записи приглашений могут существовать одновременно, а уведомления могут отправляться для каждой из них. Два callback для разных активных приглашений в одну территорию могут последовательно получить статус accepted; membership останется единственной, но журнал приглашений будет содержать несколько принятых записей.

Приоритет: низкий/средний для чистоты данных и UX. Следует определить уникальное правило для активного приглашения, например один pending invite на target_telegram_id + territory_id, и использовать его при записи, повторной отправке и принятии.


30.25. Удаление территории не очищает связанные записи голосований

deleteTerritory() вручную удаляет city_memberships, отменяет pending-приглашения, удаляет city_items и city_customization, после чего удаляет запись territories. Таблицы manager_change_requests и manager_change_votes создаются без внешних ключей на territories и друг на друга. В deleteTerritory() нет явного удаления строк этих таблиц.

Если территорию удалить во время голосования, соответствующие запрос и голоса останутся в D1. Обработчик callback позднее не сможет успешно проверить участника через isTerritoryManager() для уже удалённой территории, а фоновый scheduled handler не удаляет такие записи и не завершает голосования. Они становятся осиротевшей историей, которая не участвует в управлении существующей территорией, но остаётся в базе.

Приоритет: низкий для текущего поведения приложения, но важный для целостности и обслуживания D1. Рекомендуется явно удалять или переводить связанные голосования в cancelled при удалении территории и добавить соответствующую проверку в D1 diagnostics.


30.26. Создание заявки на территорию может вернуть ошибку после сохранения записи

createTerritory() сначала вставляет новую запись в territories со status='pending'. Только после успешного INSERT функция проверяет наличие INSPECTOR_CHAT_ID и отправляет сообщение главному инспектору через Telegram Bot API.

Если INSPECTOR_CHAT_ID не настроен, Worker возвращает HTTP 500, но созданная pending-запись уже остаётся в D1. Если Telegram sendMessage завершается ошибкой, Worker возвращает HTTP 502, но запись также не удаляется и не переводится в отдельное состояние ошибки доставки.

При повторной отправке формы frontend может создать ещё одну территорию с новым UUID, поскольку в проверенном обработчике нет ключа идемпотентности для заявки. В итоге заявитель видит ошибку, хотя заявка уже сохранена, а инспектор может не получить уведомление.

Для главного инспектора этот путь не применяется: территория сразу создаётся со status='approved' и функция возвращает успешный ответ без уведомления в инспекторский чат.

Приоритет: средний для согласованности заявок. Следует разделить сохранение заявки и доставку уведомления явным статусом доставки либо обеспечить повторяемую отправку уведомления по уже созданной заявке; клиентский повтор не должен создавать дубликат.


30.27. Гонка при первоначальном назначении владельца

claimTerritoryOwner() читает одобренную территорию и проверяет owner_telegram_id. Если поле пустое, функция выполняет UPDATE territories SET owner_telegram_id=?, owner_telegram_username=? WHERE id=?.

В UPDATE нет дополнительного условия owner_telegram_id IS NULL, а результат не проверяет, что именно этот запрос первым установил владельца. Два параллельных запроса от разных авторизованных пользователей могут одновременно прочитать пустое поле, оба пройти проверку и затем последовательно перезаписать владельца. Последний UPDATE может заменить первого заявителя.

Это усиливает описанную в разделе 30.4 проблему недостаточно строгого правила claim: даже если добавить внешнюю проверку допустимости кандидата, запись владельца должна быть защищена от конкурентного перехвата.

Приоритет: высокий для целостности прав собственности. Требуется условный атомарный UPDATE с owner_telegram_id IS NULL и обязательная проверка meta.changes; при нуле изменений обработчик должен перечитать территорию и вернуть конфликт, а не сообщать об успешном присвоении.


30.28. Параллельные сессии утверждения территорий в одном чате инспектора

startTerritoryApproval() сохраняет состояние ввода в territory_approval_sessions с первичным ключом territory_id. При этом handleTerritoryApprovalStep() выбирает сессию не по конкретному сообщению или идентификатору диалога, а по inspector_chat_id с сортировкой updated_at DESC LIMIT 1.

Если главный инспектор запустит утверждение нескольких заявок в одном чате до отправки данных по первой, в таблице будут существовать несколько сессий одного чата. Следующее текстовое сообщение будет обработано относительно самой новой сессии, независимо от того, на какой из ранее отправленных запросов инспектор отвечает. В результате данные одного города могут быть записаны в другую ожидающую заявку.

Приоритет: средний для корректности данных. Следует запретить более одной активной сессии на чат либо привязать ответ к конкретной сессии/сообщению и явно идентифицировать заявку в запросе данных.


30.29. Ошибка Telegram после утверждения оставляет территорию в частично обработанном состоянии

finalizeTerritoryApproval() сначала выполняет UPDATE territories, устанавливая status='approved' и записывая название, координаты, owner-поля и признак государственной территории. После этого функция отправляет подтверждающее сообщение в Telegram. Только после успешного завершения sendMessage выполняются назначение государственных визуалов и проверка достижений; затем вызывающая функция удаляет territory_approval_sessions.

Вызов sendMessage не обёрнут в локальный try/catch. Если Telegram API вернёт ошибку или запрос завершится исключением после успешного UPDATE, выполнение прервётся уже после утверждения территории. Государственные визуалы и проверка достижений не выполнятся, а сессия утверждения останется в таблице.

При повторном сообщении finalizeTerritoryApproval() попытается обновить только запись со status='pending'. Территория уже approved, поэтому UPDATE вернёт ноль изменений; функция сообщит, что заявка не найдена или уже обработана, и не выполнит пропущенные действия. Таким образом, обычный повтор не восстанавливает незавершённую пост-обработку.

Приоритет: средний для целостности процесса утверждения. Рекомендуется отделить фиксацию решения от уведомления и пост-обработки: после изменения статуса все обязательные операции должны быть повторяемыми и восстанавливаемыми независимо от доступности Telegram.


30.30. Не сопоставленный при утверждении владелец не привязывается автоматически после регистрации

При утверждении территории finalizeTerritoryApproval() ищет ownerUser по Telegram username и только среди пользователей со status='verified'. Если пользователь не найден, территория всё равно переводится в approved; owner_input и owner_telegram_username сохраняют введённое значение, но owner_telegram_id записывается как NULL.

Функция repairOrphanedTerritoryOwnersForUser(), вызываемая при чтении /api/me для подтверждённого пользователя, не восстанавливает такой случай: её выборка требует owner_telegram_id IS NOT NULL и ищет владельца с отсутствующим или неподтверждённым users.status. Поэтому территория с NULL owner_telegram_id и заполненным owner_input не будет автоматически сопоставлена при последующей регистрации пользователя.

В результате первоначально указанный владелец может подтвердить Minecraft-ник позднее, но это само по себе не назначит его владельцем территории. При этом POST /api/territories/claim-owner не сравнивает аккаунт с owner_input и позволяет претендовать на территорию любому авторизованному пользователю, пока owner_telegram_id остаётся NULL. Это связывает проблему с недостаточной проверкой claim, описанной в разделе 30.4.

Приоритет: высокий для корректности владения. Следует реализовать безопасное сопоставление по подтверждённому Minecraft-нику/заявленному владельцу с проверкой уникальности и атомарным назначением; общий claim endpoint не должен заменять такую проверку.


30.31. Удаление профиля не отменяет ожидающие приглашения в города

deleteManagedUser() вызывает removeManagedUserRelations(), затем удаляет строку users и запись user_directory. removeManagedUserRelations() удаляет членства, записи управляющих, личные предметы и валюту, а также завершает некоторые голосования. Однако функция не удаляет и не отменяет city_invites, где удаляемый Telegram ID указан как target_telegram_id или invited_by.

Обработчик handleResidentInviteCallback() при принятии приглашения проверяет только совпадение invite.id, target_telegram_id и status='pending'. Он не проверяет наличие пользователя в users и не требует status='verified'. Поэтому ранее отправленная Telegram-кнопка приглашения остаётся действующей после удаления профиля: тот же Telegram ID может принять приглашение, после чего обработчик создаст city_memberships даже при отсутствии строки users.

Кроме того, незавершённые приглашения, созданные удалённым пользователем как инициатором, также остаются в списке pending и отображаются управляющим в GET /api/city/management.

Приоритет: средний для согласованности удаления аккаунта и территориальных прав. При удалении профиля следует отменять все его pending-приглашения как получателя и как инициатора; callback принятия должен дополнительно проверять актуальное состояние пользователя и территории.


30.32. Неверный тип результата в ветках ошибок авторизации API

requireUser() и requireMainInspector() возвращают не Response напрямую, а объект-обёртку вида { error: Response }. requireVerifiedUser() использует тот же контракт и также возвращает объект с полем error при отказе.

В worker.js обнаружено 52 API-обработчика, которые при auth.error возвращают сам объект auth вместо auth.error. Среди них обработчики управления территориями и жителями, профилем, рейтингами, комментариями, скриншотами, казной, кастомизацией, событиями и административными функциями. Примеры: getMe(), claimNickname(), claimTerritoryOwner(), inviteResident(), removeResident(), promoteResident(), demoteManager(), updateTerritoryOwner(), updateTerritoryManager(), treasuryDeposit(), purchaseCustomizationItem(), saveRating() и другие.

Внешний fetch handler после выполнения маршрута предполагает, что результат — объект Response: читает response.headers, response.status, response.body и создаёт новый Response. Если обработчик вернул {error: Response}, это обычный JavaScript-объект без этих полей. Он не вызывает предусмотренную внутреннюю обработку исключений; при последующей нормализации отсутствующий status передаётся конструктору Response как undefined, что приводит к ответу по умолчанию со статусом 200 и пустым телом вместо исходного 401 или 403.

Обработчики, которые возвращают auth.error, работают с правильным типом результата. В частности, в том же Worker встречаются корректные варианты в getAdminGlobalSettings(), saveAdminGlobalSetting(), getUserSettings(), saveUserSettings(), leaveTerritory(), saveCityAdditionalInfo(), getEvents(), createEvent(), updateEvent(), deleteEvent(), saveEventReminder() и getD1Diagnostics(). Вспомогательные функции requireVerifiedUser() и requireMainInspector() намеренно передают объект auth с полем error вызывающему обработчику; ошибка возникает именно там, где конечный route handler возвращает этот wrapper вместо содержащегося в нём Response.

Последствие: для неавторизованных запросов к затронутым маршрутам клиент может получить пустой HTTP 200. Frontend parseApiResponse() сначала пытается разобрать JSON, затем считает отсутствие тела ошибочным ответом даже при response.ok=true и показывает fallback-сообщение о некорректном ответе. Поэтому пользователь обычно увидит ошибку операции, но HTTP-статус и тело не позволят клиенту правильно различить 401, 403 и техническую проблему. Само по себе это не предоставляет права на выполнение защищённой операции: бизнес-логика до проверки авторизации не продолжается.

Приоритет: высокий для корректности авторизации и HTTP-контракта. Следует унифицировать все конечные обработчики: при auth.error возвращать auth.error. После исправления необходимо проверить все 401/403 ветви тестами, включая requireUser, requireVerifiedUser и requireMainInspector, и убедиться, что клиент получает исходный статус и JSON-тело ошибки.

======================================================================
31. ЗАКЛЮЧЕНИЕ
======================================================================

Voxygen представляет собой модульную Telegram Mini App систему, в которой пользовательский интерфейс, серверная бизнес-логика, постоянные данные и тяжёлые графические ресурсы разделены между отдельными компонентами.

Frontend Worker отвечает за доступность приложения. Основной Worker проверяет Telegram-пользователей, выполняет правила доступа, обслуживает API, работает с D1 и Telegram Bot API. D1 хранит прикладные данные. Отдельный map-assets Worker отдаёт статические графические ресурсы карты.

Ключевая особенность картографической подсистемы — разделение исходной карты и опубликованной пирамиды детализации. Оригинал загружается в GitHub Release, автоматический workflow создаёт preview и WebP-тайлы, а клиент загружает только те уровни и фрагменты, которые нужны текущему viewport.

Остальные подсистемы используют ту же серверную модель: клиент запрашивает действие, backend проверяет пользователя, роль и право на конкретный объект, после чего меняет D1 и при необходимости отправляет уведомления через Telegram.

Такое разделение позволяет развивать интерфейс, серверную логику, экономику и обработку карты независимо, сохраняя единые правила доступа и постоянное хранилище данных.
