======================================================================
0. НАЗНАЧЕНИЕ ДОКУМЕНТА И ПРАВИЛА ЧТЕНИЯ
======================================================================

Этот документ описывает Voxygen как целую систему: пользовательский интерфейс, серверную логику, Telegram-интеграцию, базу данных, систему территорий и рейтингов, городское управление, экономику, визуальную кастомизацию, события и подсистему интерактивной карты.

Документ составлен по текущим исходным файлам репозиториев, а не только по ранее подготовленному описанию карты. Если поведение интерфейса, настройки инфраструктуры или внешние секреты нельзя подтвердить чтением репозитория, это отдельно отмечается. Наличие имени секрета в коде не означает, что его значение или работоспособность настройки были проверены.

Главные исходные файлы:
- CounterBoard/Voxygen/src/App.jsx — пользовательское приложение и большая часть клиентской логики.
- CounterBoard/Voxygen/src/main.jsx — запуск React-приложения и инициализация Telegram Web App.
- CounterBoard/Voxygen/bot/src/worker.js — основной backend Worker, API, Telegram webhook, бизнес-логика и миграции D1.
- CounterBoard/Voxygen/bot/schema.sql — базовая схема D1; фактическая схема шире и дополняется миграциями Worker.
- CounterBoard/Voxygen/shared/world-map-coordinates.js — общая геометрия мира и функции координат/масштаба.
- CounterBoard/Voxygen-map-assets/tools/build_map.py — генератор Deep Zoom.
- CounterBoard/Voxygen-map-assets/.github/workflows/publish-map.yml — автоматическая обработка и публикация карты.
- CounterBoard/Voxygen-map-assets/public/_headers — HTTP-заголовки статических ресурсов.
- CounterBoard/Voxygen-map-assets/wrangler.jsonc — конфигурация Worker статических ресурсов.

Документация описывает именно текущую архитектуру. Она не является инструкцией по восстановлению секретов и не содержит секретных значений.

======================================================================
1. ОБЩАЯ АРХИТЕКТУРА
======================================================================

Voxygen — Telegram Mini App с React-интерфейсом, серверной логикой на Cloudflare Workers и постоянными данными в Cloudflare D1.

В системе используются три Cloudflare Worker, два GitHub-репозитория и одна основная база Cloudflare D1.

1.1. Worker voxygenebot — публикация пользовательского интерфейса

Адрес:
https://voxygenebot.counterboard.workers.dev

Назначение:
- отдача собранного фронтенда Voxygen;
- загрузка HTML, JavaScript и остальных статических файлов приложения;
- запуск интерфейса внутри Telegram Web App;
- отображение разделов приложения и интерактивной карты.

Конфигурация:
CounterBoard/Voxygen/wrangler.jsonc

Основные параметры:
- name: voxygenebot;
- assets.directory: ./dist.

Сборка фронтенда выполняется Vite. Результат сборки помещается в dist и публикуется как статические Assets Worker.

1.2. Worker voxygen — основной backend

Адрес:
https://voxygen.counterboard.workers.dev

Назначение:
- проверка Telegram Web App Init Data;
- определение пользователя и его роли;
- предоставление API для всех основных функций приложения;
- управление территориями, пользователями, рейтингами и комментариями;
- городское управление, приглашения и роли жителей;
- казна, персональные балансы и финансовые операции;
- каталог визуальных предметов и достижения;
- события и напоминания;
- настройки пользователя и глобальные настройки;
- загрузка исходной карты в GitHub Releases;
- выдача исходной карты в резервном режиме;
- обработка Telegram webhook и команд банковского пользователя.

Исходный файл:
CounterBoard/Voxygen/bot/src/worker.js

Конфигурация:
CounterBoard/Voxygen/bot/wrangler.toml

1.3. Worker voxygen-map-assets — публикация графических ресурсов карты

Адрес:
https://voxygen-map-assets.counterboard.workers.dev

Назначение:
- выдача manifest.json;
- выдача preview.webp;
- выдача Deep Zoom WebP-тайлов;
- обслуживание запросов статических файлов;
- CORS и cache headers.

Worker публикует каталог public репозитория CounterBoard/Voxygen-map-assets через Workers Static Assets.

1.4. GitHub-репозитории

Основной репозиторий:
CounterBoard/Voxygen

Содержит:
- React-приложение;
- основной backend Worker;
- SQL-базовую схему D1;
- общие функции геометрии карты;
- тесты;
- конфигурации Workers и Vite.

Репозиторий обработки карты:
CounterBoard/Voxygen-map-assets

Содержит:
- скрипт генерации Deep Zoom;
- GitHub Actions workflow обработки карты;
- конфигурацию voxygen-map-assets Worker;
- правила HTTP-заголовков;
- документацию контракта загрузчика карты.

Репозиторий исходников карты:
CounterBoard/Voxygen-map-storage

Используется для хранения оригиналов карты как GitHub Release Assets. Это не репозиторий исходного кода приложения.

Release tag:
world-map

1.5. Cloudflare D1

Имя базы:
voxygen

Binding в основном Worker:
DB

D1 является постоянным хранилищем структурированных данных приложения. В ней находятся пользователи, территории, роли, оценки, комментарии, городские связи, экономика, события, настройки и ссылки на исходник карты.

D1 не используется для хранения Deep Zoom-тайлов. Готовые тайлы и превью публикуются как статические ресурсы отдельного Worker.

1.6. Общий маршрут запросов

Пользователь открывает Telegram Mini App:
Telegram → voxygenebot → React-приложение.

Когда приложению нужны данные:
React-приложение → voxygen API → проверка Telegram Init Data → D1 / Telegram Bot API / GitHub API.

Для карты:
React-приложение → voxygen-map-assets → manifest и preview → необходимые тайлы.

Для загрузки новой карты:
Главный инспектор → voxygenebot → voxygen → GitHub Release → GitHub Actions в Voxygen-map-assets → генерация Deep Zoom → публикация в voxygen-map-assets → обновлённый manifest → клиент.

2. ФРОНТЕНД И ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС
======================================================================

2.1. Технологии

Фронтенд использует:
- React 18;
- React DOM;
- Vite 6;
- lucide-react для иконок.

Основные команды package.json:
- npm run dev — локальный режим разработки;
- npm run build — сборка фронтенда в dist;
- npm run preview — локальный просмотр собранной версии;
- npm test — запуск тестов Node.js.

Точка входа:
src/main.jsx

Она сообщает Telegram Web App, что приложение готово, вызывает expand() и монтирует React-компонент приложения.

Основная реализация интерфейса находится в одном крупном файле:
src/App.jsx

2.2. Адреса backend и карты

В клиентском коде заданы:
API_BASE = https://voxygen.counterboard.workers.dev
MAP_ASSETS_BASE = https://voxygen-map-assets.counterboard.workers.dev

Фронтенд напрямую обращается к основному API и к Worker картографических ресурсов.

2.3. Основная навигация

Нижняя навигация содержит четыре раздела:

1. Визуал
   Каталог визуальных предметов, инвентарь, покупка, оформление территорий и управление предметами в пределах прав пользователя.

2. Территории
   Основной раздел с тремя внутренними вкладками:
   - Набор — список открытых объявлений о наборе жителей;
   - Карта — интерактивная карта с маркерами территорий;
   - Рейтинг — список территорий, отсортированный по рейтинговым показателям.

3. Ивенты
   Список событий, создание и управление событиями в соответствии с ролью пользователя, напоминания.

4. Профиль
   Minecraft-никнейм и статус его подтверждения, персональные настройки, данные городов пользователя, городское управление, доступные административные инструменты.

2.4. Карточка территории

Карточка/страница территории объединяет сведения о городе и инструменты взаимодействия:
- название и координаты;
- владелец, основатели/мэры и жители;
- рейтинг и оценки;
- комментарии и ответы;
- скриншоты;
- дополнительная информация;
- объявление о наборе;
- казна и финансовые действия;
- управление городом;
- визуальное оформление города.

Конкретный набор действий зависит от роли пользователя и его отношения к выбранной территории.

2.5. Стилизация текста Minecraft

В интерфейсе есть обработка форматирования Minecraft:
- цветовые коды;
- жирный, курсивный, подчёркнутый и зачёркнутый текст;
- обфускация;
- шестнадцатеричные цветовые коды.

Это применяется к названиям и текстам, где допустимо Minecraft-форматирование. Отдельно реализована обработка Telegram username и ссылок на Telegram.

======================================================================
3. АВТОРИЗАЦИЯ, ПОЛЬЗОВАТЕЛИ И РОЛИ
======================================================================

3.1. Авторизация через Telegram

Клиент получает Telegram Web App Init Data из Telegram WebApp API.

Для API-запросов Init Data передаётся:
- обычно через заголовок X-Telegram-Init-Data;
- для некоторых JSON-запросов также может присутствовать в поле initData.

Основной Worker использует BOT_TOKEN и функцию verifyInitData().

Проверка включает:
1. разбор параметров Init Data;
2. извлечение hash;
3. сортировку параметров;
4. формирование data-check-string;
5. вычисление HMAC-SHA-256 по алгоритму Telegram Web Apps;
6. сравнение рассчитанной подписи с переданной;
7. проверка auth_date: Init Data должно быть не старше 24 часов и не может быть более чем на 60 секунд из будущего;
8. разбор JSON-поля user.

Отсутствующий или некорректный auth_date, просроченная подпись либо неверная подпись приводят к отказу в авторизации. Это ограничивает повторное использование ранее перехваченного Init Data.

3.2. Роли

В системе используются три основные роли:

Пользователь (user):
- обычный участник приложения;
- может просматривать доступные территории;
- после подтверждения Minecraft-ника получает доступ к действиям, для которых требуется verified-профиль;
- может вступать в города, оценивать территории и участвовать в разрешённых пользовательских функциях.

Инспектор (inspector):
- роль хранится в таблице inspectors;
- имеет доступ к инспекторским функциям, включая инспекторские оценки;
- не равнозначен главному инспектору.

Главный инспектор (main_inspector):
- определяется через INSPECTOR_CHAT_ID;
- настройка может содержать Telegram ID либо username;
- имеет расширенные административные права;
- управляет инспекторами, территориями, пользователями, глобальными настройками и публикацией карты;
- некоторые административные операции доступны исключительно этой роли.

Проверки прав выполняются на backend. Скрытие кнопки в интерфейсе не является единственным механизмом защиты.

3.3. Подтверждение Minecraft-ника

В профиле пользователь указывает Minecraft-никнейм.

Сервер хранит:
- Telegram ID;
- Telegram username;
- Minecraft nickname;
- статус пользователя;
- при наличии — XUID;
- идентификатор текстуры скина;
- время проверки скина.

Для ряда действий используется requireVerifiedUser(): кроме корректной Telegram-авторизации требуется подтверждённый статус и непустой Minecraft-никнейм.

Поддерживается предварительная регистрация пользователей с Minecraft-ником и Telegram username. При подтверждении соответствующего аккаунта сервер может связать его с предварительно зарегистрированными данными.

3.4. Синхронизация Telegram username

Worker синхронизирует Telegram username пользователя в таблице users и связанных записях. При обработке сообщений и callback_query webhook обновляет сведения об отправителе.

Username используется как контактная информация и как один из способов разрешения имени пользователя, но основным идентификатором аккаунта остаётся Telegram ID.

3.5. Права основателя и мэра

Владелец территории определяется по owner_telegram_id.
Дополнительные управляющие хранятся в territory_managers.

Функция isTerritoryManager() считает управляющим:
- владельца утверждённой территории;
- пользователя, присутствующего в territory_managers.

Основатель и мэр могут управлять городом в пределах серверных проверок.

3.6. Жители и членство в нескольких городах

Членство хранится в city_memberships с составным ключом:
telegram_id + territory_id.

Схема поддерживает принадлежность одного пользователя к нескольким территориям. В Worker предусмотрена миграция со старой схемы одиночного членства.

Для приглашений используется city_invites. Приглашение может быть отправлено уже зарегистрированному пользователю или сохранено до подтверждения Minecraft-ника адресата. Активные приглашения ограничены парой «территория + Telegram ID» либо «территория + Minecraft nickname»; повторное приглашение в той же территории заменяет прежнее ожидающее приглашение. Отмена приглашения не затрагивает другие территории пользователя.

======================================================================
4. ТЕРРИТОРИИ: СОЗДАНИЕ, ПРОВЕРКА И УПРАВЛЕНИЕ
======================================================================

4.1. Создание территории

Клиент отправляет данные через:
POST /api/territories

Обычный пользователь должен иметь подтверждённый Minecraft-никнейм. Главный инспектор может создавать территорию напрямую.

Проверяются:
- название;
- данные владельца;
- координаты X и Z;
- допустимый диапазон координат;
- длина текстовых полей.

Допустимые координаты:
Фактический диапазон системы:
X: от -3008 до 3007 включительно;
Z: от -3008 до 3007 включительно.

Обычная заявка получает статус pending. Территория, созданная главным инспектором, может сразу получить статус approved.

4.2. Telegram-процесс утверждения

Для заявок обычных пользователей Worker отправляет сообщение главному инспектору через Telegram Bot API.

Главный инспектор может начать процесс утверждения через inline-кнопку. Затем Worker создаёт сессию territory_approval_sessions и запрашивает сообщение из трёх строк:
1. название территории;
2. @username основателя/мэра;
3. X Z — две координаты.

Для государственной территории вместо username используется специальное значение Multi-Punk.

Для одного Telegram-чата допускается только одна активная сессия утверждения; при запуске новой сессии предыдущая сессия этого чата закрывается. Уникальный индекс D1 закрепляет это ограничение.

После проверки сервер сохраняет утверждённую территорию. Локальные post-processing операции (например, подбор государственных визуалов и проверка достижений) выполняются до отправки итогового сообщения. Сбой Telegram-уведомления не отменяет уже сохранённое утверждение.

4.3. Государственные территории

У территории есть признак is_government.

Государственные территории имеют отдельные ограничения:
- некоторые функции городского управления для них недоступны;
- они используют соответствующий тип маркера;
- обычные пользователи не могут создавать от имени государственной территории некоторые виды событий;
- оформление обычного города не применяется к государственной территории.

4.4. Административные операции с территориями

Главный инспектор может:
- переименовать территорию;
- удалить территорию;
- изменить координаты;
- изменить владельца;
- изменить управляющего/мэра;
- управлять заявками и инспекторами.

Передача владельца и управляющих выполняется пакетами D1 batch, чтобы связанные изменения owner_telegram_id, territory_managers и city_memberships применялись атомарно. Самостоятельное получение незанятой роли владельца допускается только при совпадении owner_input с подтверждённым Minecraft nickname или Telegram username пользователя; назначение выполняется условным UPDATE при owner_telegram_id IS NULL.

Серверные маршруты этих действий находятся в группе /api/admin/territories/*.

4.5. Дополнительная информация

Основатель или мэр утверждённой негосударственной территории может сохранить дополнительную информацию через:
POST /api/city/additional-info

Максимальная длина поля в текущем backend:
542 символа.

Для государственной территории поле недоступно.

======================================================================
5. ГОРОДСКОЕ УПРАВЛЕНИЕ И ПРИГЛАШЕНИЯ
======================================================================

5.1. Управление жителями

Основатель/мэр может:
- приглашать пользователя в город;
- отменять приглашение;
- удалять жителя;
- назначать жителя мэром/управляющим;
- снимать полномочия мэра;
- просматривать список жителей, управляющих и приглашений.

Основные маршруты:
- POST /api/city/invite
- POST /api/city/invite/cancel
- POST /api/city/remove-resident
- POST /api/city/promote-resident
- POST /api/city/demote-manager
- POST /api/city/leave
- GET /api/city/management

5.2. Приглашения

Приглашения отправляются через Telegram Bot API с кнопками согласия и отказа.

Если Minecraft-ник ещё не связан с подтверждённым пользователем, приглашение может быть сохранено в ожидании подтверждения ника. После появления подходящего аккаунта Worker может отправить приглашение.

Для контроля доставки используются поля notification_sent_at и notification_claimed_at. Worker атомарно захватывает отправку, отмечает время только после успешного ответа Telegram и не повторяет успешно доставленное приглашение при каждом новом сообщении пользователя. Неуспешная отправка может быть повторена после истечения короткой блокировки.

Существуют приглашения типа join и transfer. Состояние приглашения хранится в city_invites. Удаление пользователя отменяет ожидающие приглашения, адресованные ему или созданные им; callback старой кнопки дополнительно проверяет, что Telegram-аккаунт адресата всё ещё существует и имеет статус verified.

5.3. Изменение состава управляющих

Изменение управляющего может требовать процедуры согласования между текущими основателями/мэрами территории.

Для этого используются:
- manager_change_requests;
- manager_change_votes.

Запрос имеет статус, инициатора, целевого пользователя, срок действия и параметры голосования. Инициатор учитывается как один голос за предложенное изменение. Остальные управляющие голосуют через Telegram callback. Scheduled Worker запускается каждую минуту и завершает просроченные запросы, даже если после истечения срока никто не нажал кнопку.

При положительном решении сначала применяется изменение ролей. Статус approved записывается только после подтверждения успешного применения; если применить изменение невозможно, запрос отклоняется. Переходы между city_memberships и territory_managers выполняются через D1 batch.

5.4. Уход из города

Пользователь может покинуть территорию через соответствующий маршрут. Сервер проверяет текущие отношения пользователя с территорией и применяет правила членства/управления.

======================================================================
6. РЕЙТИНГ ТЕРРИТОРИЙ
======================================================================

6.1. Критерии

Оценка территории состоит из четырёх параметров:
- integrity;
- comfort;
- atmosphere;
- detail.

Каждый параметр принимает целое значение от 1 до 5.

Итоговая оценка одной анкеты:
(integrity + comfort + atmosphere + detail) × 0.5

Максимальный итог одной анкеты — 10 баллов.

6.2. Два потока оценок

Оценки обычных пользователей хранятся в ratings.
Оценки инспекторов хранятся отдельно в inspector_ratings.

Оценка обычного пользователя требует подтверждённого Minecraft-ника.

Основатель/мэр территории не может оценивать собственный город как обычный пользователь. Для инспекторской роли действует отдельная ветка расчёта.

6.3. Вес жителей

Если пользователь является жителем оцениваемой территории, его оценка получает вес 1/3. Оценка пользователя, не являющегося жителем, получает обычный вес 1.

6.4. Учёт свежих оценок

Оценки сортируются от новых к старым.

Для инспекторской оценки:
- последние две оценки образуют группу новых;
- остальные — группу старых;
- если есть старые оценки, среднее новых и среднее старых получают по 50% веса.

Для пользовательской оценки:
- последние пять оценок образуют группу новых;
- остальные — группу старых;
- при наличии обеих групп они получают по 50% веса.

Внутри каждой группы применяется вес оценки жителя, если он относится к территории.

6.5. Ограничение частоты

Повторное обновление оценки одним пользователем для одной территории ограничено интервалом 20 часов.

Если ограничение ещё действует, API возвращает HTTP 429, время следующей попытки и ранее сохранённые значения оценки. Проверка времени встроена в условие UPSERT, поэтому параллельные запросы не могут обойти интервал в 20 часов.

6.6. Сортировка

Экран рейтинга использует рассчитанные показатели территории. Backend возвращает данные рейтинга и число пользовательских голосов.

7. КОММЕНТАРИИ, ОТВЕТЫ И СКРИНШОТЫ
======================================================================

7.1. Комментарии

Для территорий поддерживаются:
- получение списка комментариев;
- добавление комментария;
- редактирование;
- удаление;
- ответы на комментарии;
- редактирование и удаление ответов.

Основные таблицы:
- comments;
- comment_replies.

Сервер хранит Telegram ID автора, username (если доступен), текст, роль и время создания. Длина комментария и ответа ограничена 4000 символами; тот же предел применяется при редактировании ответа. На один комментарий допускается один редактируемый ответ. Создание ответа и уведомление о первом ответе защищены от параллельного дублирования; удаление комментария и ответа выполняется одним D1 batch.

7.2. Скриншоты

Пользователь может отправить скриншот территории.

В таблице screenshots сохраняются:
- ID;
- территория;
- Telegram ID и username отправителя;
- Telegram file_id и file_unique_id;
- статус;
- время создания;
- данные модерации.

Поддерживаются получение, выдача файла, модерация и удаление скриншотов. Для взаимодействия с Telegram используются file_id и Telegram Bot API. Загрузчик принимает JPEG, который формирует клиентский компрессор, и ограничивает размер исходного файла. Модерация является одноразовым переходом только из pending; повторное нажатие старой Telegram-кнопки не может изменить уже принятое решение. HTTP-маршрут модерации принимает явное поле approve (boolean) либо status (approved/rejected). Если скриншот автоматически получает approved от инспектора, проверка достижений также запускается после сохранения.

9. СОБЫТИЯ И НАПОМИНАНИЯ
======================================================================

9.1. События

События хранятся в таблице events.

Данные события включают:
- название;
- связанную территорию (если есть);
- место;
- дату и время;
- координаты;
- описание;
- изображение;
- внешнюю ссылку;
- часовой пояс события;
- автора;
- время создания и обновления;
- активность.

Основные маршруты:
- GET /api/events
- POST /api/events
- PATCH /api/events
- DELETE /api/events

Обычный пользователь может создавать событие от территории, если является её основателем/мэром или жителем. Для государственной территории действуют отдельные ограничения. Главный инспектор имеет расширенные права.

Если территория выбрана, место события берётся из её проверенного названия, а не доверяется произвольному тексту клиента.

9.2. Напоминания

Пользователь может создать или удалить напоминание о событии:
- POST /api/events/reminder
- DELETE /api/events/reminder

Таблица event_reminders хранит:
- событие и пользователя;
- величину и единицу времени до события;
- рассчитанное время отправки;
- статус;
- количество попыток;
- время следующей попытки;
- claim token;
- время успешной отправки.

9.3. Фоновая обработка

В bot/wrangler.toml установлен Cron:
* * * * *

То есть scheduled handler запускается каждую минуту.

Он:
- проверяет напоминания, которые пора отправить;
- отправляет уведомления через Telegram Bot API;
- обрабатывает повторные попытки;
- атомарно удаляет просроченные события вместе с напоминаниями и устаревшими ключами идемпотентности создания событий;
- завершает просроченные голосования за изменение управляющих;
- повторяет отправку ожидающих приглашений жителям, если предыдущая попытка не была успешно доставлена.

События, завершившиеся более чем 24 часа назад, очищаются. Напоминания удаляются перед удалением соответствующих событий. Записи event_create_requests старше 30 дней также очищаются.

9.4. Защита от повторного создания

При создании события используется requestKey и хэш содержимого запроса. Это позволяет распознавать повторную отправку одного и того же действия при сетевых повторах.

10. ВИЗУАЛЬНАЯ КАСТОМИЗАЦИЯ И ДОСТИЖЕНИЯ

10.1. Каталог предметов

Система визуальных предметов позволяет создавать, покупать, хранить и использовать оформление.

Основные таблицы:
- customization_categories;
- customization_items;
- user_items;
- city_items;
- city_customization.

Предметы имеют категории, названия, цену, изображение, активность и дополнительные признаки. Для предметов могут задаваться теги/категории, сортировка и видимость.

10.2. Управление каталогом

Главный инспектор имеет инструменты создания и редактирования визуальных предметов:
- создание предмета;
- редактирование;
- удаление;
- включение/выключение видимости;
- сортировка предметов;
- сортировка тегов/категорий;
- управление категориями и специальными признаками маркеров.

Изображения предметов выдаются через API Worker. При создании и редактировании сервер проверяет тип и допустимые характеристики изображения.

10.3. Персональные предметы и баланс

У пользователя есть баланс самоцветов и приобретённые предметы.

Баланс хранится в user_currency.
Приобретённые предметы — в user_items.

Покупка списывает средства, добавляет предмет в личный или городской инвентарь и записывает расход в gem_spend_log в одном D1 batch. Если запись журнала не может быть сохранена, вся покупка откатывается.

10.4. Оформление города

Город может использовать:
- маркер территории;
- фон/элемент оформления.

Настройки города хранятся в city_customization. Менять оформление могут основатель и мэры. Для государственных территорий обычное городское оформление недоступно.

Маркер проверяется по совместимости с типом территории: обычный или государственный.

10.5. Достижения

Система достижений оценивает требования территории и может автоматически выдавать визуальные награды.

Используются:
- функция расчёта условий;
- проверка требований;
- повторная проверка достижений;
- таблица achievement_awards для фиксации выданных наград.

Главный инспектор может инициировать повторную проверку через:
POST /api/achievements/recheck

11. САМОЦВЕТЫ, ЛИЧНЫЙ БАЛАНС И КАЗНА ГОРОДА
======================================================================

11.1. Балансы

Личный баланс:
user_currency

Казна территории:
city_treasury

Операции:
financial_operations

Дополнительный журнал Telegram-банковских операций:
bank_transactions

11.2. Пополнение казны

Маршрут:
POST /api/treasury/deposit

Пополнять казну могут участники соответствующей территории, включая управляющих, при соблюдении серверных проверок.

11.3. Пожертвование

Маршрут:
POST /api/treasury/donate

Операция выполняется через серверную финансовую логику. Точные допустимые стороны перевода и ограничения определяются обработчиком и проверяются backend, а не клиентом.

11.4. Снятие средств

Маршрут:
POST /api/treasury/withdraw

Снимать средства из казны может основатель или мэр соответствующей территории. Сервер проверяет наличие средств.

11.5. Идемпотентность

Финансовые операции используют operationId и запись в financial_operations. Это нужно, чтобы повторный запрос после потери ответа не списывал средства повторно.

На клиенте незавершённый токен операции сохраняется в localStorage/sessionStorage, когда это возможно. Пока исходная операция не подтверждена, клиент блокирует отправку изменённой суммы для того же действия и получателя.

11.6. Telegram-банковский пользователь

В Worker предусмотрен отдельный режим банковского пользователя, задаваемый секретом BANKER_TELEGRAM_ID.

Webhook проверяет ID отправителя. Для разрешённого пользователя распознаются текстовые команды перевода, пополнения или списания. Получатель может разрешаться как игрок по Minecraft-нику/Telegram username либо как территория по названию.

Повторные Telegram update_id не должны приводить к повторному проведению одной операции: update_id уникален в bank_transactions. Изменение баланса и перевод записи журнала в success/rejected выполняются в одном D1 batch. Если Worker остановился после создания записи processing, повторный webhook может безопасно продолжить обработку; если перевод уже завершён, повтор не меняет баланс. Ошибка после фиксации перевода не может перезаписать success статусом failed.

После обработки Worker отправляет ответ в Telegram и сохраняет статус операции.

12. ПЕРСОНАЛЬНЫЕ И ГЛОБАЛЬНЫЕ НАСТРОЙКИ
======================================================================

12.1. Персональные настройки

Маршруты:
- GET /api/user-settings
- POST /api/user-settings

Хранятся:
- тема;
- часовой пояс;
- масштаб карты;
- настройки уведомлений о событиях;
- индивидуальные настройки уведомлений по территориям.

Основная таблица:
user_preferences

Таблица территориальных уведомлений:
territory_notification_preferences

Текущая тема, доступная в коде:
vox

Часовой пояс по умолчанию:
UTC+3

Масштаб карты по умолчанию:
88%

Диапазон ползунка:
1–100%.

Преобразование процента в реальный масштаб экспоненциальное:
100% = 1x;
1% = 24x.

Формула:
scale = 24 ^ ((100 - percent) / 99)

Таким образом, равные шаги ползунка дают одинаковое относительное изменение масштаба. Значение 88% соответствует приблизительно 1.46x.

12.2. Уведомления

Поддерживаются уведомления о событиях и индивидуальные настройки уведомлений по территориям.

Для территориальных уведомлений:
- если у пользователя есть явная запись в territory_notification_preferences, используется она;
- если записи нет, управляющий территории получает уведомления по умолчанию;
- обычный житель без явной настройки не получает такие уведомления по умолчанию.

Старый общий переключатель уведомлений сохранён для совместимости с предыдущими версиями клиента, но больше не управляет отдельным глобальным режимом уведомлений.

12.3. Глобальные настройки

Маршруты:
- GET /api/admin/global-settings
- POST /api/admin/global-settings

Доступны только главному инспектору.

Поддерживаются отдельные ключи:
- map_zoom — глобальный масштаб карты;
- theme — глобальная тема.

Таблица:
global_setting_overrides

Каждый параметр хранит:
- значение;
- время окончания действия или NULL для постоянного значения;
- время обновления;
- ID главного инспектора, изменившего настройку.

Масштаб и тема применяются и снимаются независимо. Для каждого параметра можно установить срок действия или включить постоянный режим. Допустимый срок — до 10 лет.

Глобальное значение является временным значением по умолчанию/переопределением, а не безусловной блокировкой пользовательского выбора.

Если пользователь меняет конкретный параметр во время действия глобального значения, backend записывает отдельную отметку для этого параметра и пользователь продолжает использовать собственное значение. Второй параметр при этом не затрагивается.

После окончания срока глобального значения пользователь возвращается к своему личному значению, если не сделал собственный выбор во время действия соответствующего глобального режима.

Отметка пользовательского выбора привязана к версии конкретного глобального изменения через updated_at. При создании нового глобального изменения с новым updated_at новое значение может снова примениться к пользователю.

13. ИНТЕРАКТИВНАЯ КАРТА: ГЕОМЕТРИЯ И ОТОБРАЖЕНИЕ
======================================================================

13.1. Компонент карты

Основной React-компонент:
VoxMap

Расположен в:
src/App.jsx

Карта отображается во вкладке «Карта» раздела «Территории».

Внешняя область карты квадратная. Изображение карты служит базовым слоем, поверх него размещаются детальные тайлы и маркеры территорий.

13.2. Координатная система мира

Текущая геометрия определяется в:
shared/world-map-coordinates.js

Тип:
minecraft-world-block-centers

Границы:
minX = -3008
maxX = 3007
minZ = -3008
maxZ = 3007

Количество координатных позиций по каждой оси:
6016

Геометрия фиксирована и не зависит от пиксельного разрешения изображения карты.

Координаты переводятся в проценты с учётом центров блоков:
xPercent = ((x - minX + 0.5) / worldWidth) × 100
yPercent = ((z - minZ + 0.5) / worldHeight) × 100

Невалидные координаты не переводятся в положение маркера.

Старые manifest без coordinateSystem остаются совместимыми. Если manifest содержит координатную систему, клиент проверяет её соответствие текущим границам.

13.3. Маркеры территорий

Маркеры отображаются отдельным слоем над картой.

Для территории используются её координаты X/Z. Размер маркера визуально компенсирует увеличение карты обратным коэффициентом:
1 / scale

Это не позволяет значкам чрезмерно увеличиваться вместе с картой.

Могут использоваться:
- выбранный визуальный предмет-маркер;
- стандартный маркер, если пользовательский не задан.

Для государственных территорий применяется совместимый тип государственного маркера.

Маркер открывает страницу соответствующей территории. Слой маркеров включается после готовности необходимых данных.

13.4. Загрузка карты в клиенте

При открытии вкладки карты вызывается loadWorldMap().

Сначала выполняется:
GET https://voxygen-map-assets.counterboard.workers.dev/world-map/manifest.json

К запросу добавляется параметр check с текущим временем, используется cache: no-store.

Проверяется:
- наличие mapVersion;
- наличие source;
- поддерживаемый source.type;
- размеры источника Deep Zoom;
- совместимость coordinateSystem;
- наличие previewUrl.

Поддерживаемые клиентские типы:
- deepzoom;
- url-grid.

Если manifest корректен, клиент загружает preview, декодирует его и устанавливает как базовое изображение. Затем VoxMap использует параметры источника для подгрузки тайлов.

13.5. Резервный путь

Резервная выдача цельного изображения используется только в случае HTTP 404 для manifest.

В этом случае клиент:
1. отправляет HEAD на /api/map;
2. проверяет Content-Type и X-Map-Version;
3. загружает изображение GET-запросом с параметром версии.

Если manifest существует, но он некорректен или недоступен с другой ошибкой, клиент не должен обходить его через старый путь. Это предотвращает незаметное использование устаревшей карты при проблемах новой публикации.

Резервный путь выдаёт целое изображение, а не Deep Zoom-тайлы.

16. АВТОМАТИЧЕСКАЯ ОБРАБОТКА DEEP ZOOM

16.1. Workflow

Репозиторий:
CounterBoard/Voxygen-map-assets

Process and publish world map

Триггер:

Worker вызывает GitHub API:
POST /repos/CounterBoard/Voxygen-map-assets/actions/workflows/publish-map.yml/dispatches

main

Успешный запуск workflow ожидает HTTP 204.

16.2. Параметры GitHub Actions

- Ubuntu latest;
- Python 3.12;
- Pillow и Requests;
- Node.js 22;
- Wrangler latest;
- timeout job: 30 минут;
- concurrency group: world-map-publish;
- cancel-in-progress: false.

Параллельный запуск не отменяет автоматически уже выполняющуюся обработку.

16.3. Проверка исходного URL

Workflow принимает только HTTPS URL с доменом github.com и путём, начинающимся с:
 /CounterBoard/Voxygen-map-storage/releases/download/

Это не позволяет подставить произвольный внешний URL.

Загрузка исходника выполняется потоково блоками по 1 МБ.

Если репозиторий с исходником приватный, может использоваться MAP_SOURCE_GITHUB_TOKEN. Для публичного репозитория он не обязателен.

При перенаправлении на отдельный адрес скачивания GitHub токен не передаётся на этот адрес.

16.4. Скрипт генерации

Файл:
tools/build_map.py

Библиотека:
Pillow

Параметры:
- TILE_SIZE = 512;
- PREVIEW_MAX = 1200;
- MAX_RASTER_DIMENSION = 8944; MAX_RASTER_PIXELS = 80 000 000.

Текущий генератор принимает квадратную карту. Это требование сохраняет одинаковый масштаб игрового пространства по осям X и Z.

Размер каждой стороны должен быть от 1 до 8944 пикселей, общий предел — 80 000 000 пикселей. Для квадратной карты 8944×8944 составляет 79 995 136 пикселей. Проверка общего pixel budget нужна, чтобы ограничение было согласовано с Pillow decompression-bomb protection.

16.5. Подготовка изображения

Генератор:
1. открывает исходное изображение через Pillow и проверяет фактический формат PNG, JPEG или WebP;
2. получает width и height без преобразования всего изображения в RGBA;
3. проверяет диапазон каждой стороны 1–8944 пикселя;
4. проверяет общий pixel count: width × height не должен превышать 80 000 000;
5. проверяет квадратность;
6. только после этих проверок применяет EXIF orientation;
7. преобразует проверенное изображение в RGBA.

Такой порядок не создаёт большую RGBA-копию изображения до проверки pixel budget.

16.6. Превью

Копия исходника уменьшается так, чтобы стороны не превышали 1200 пикселей.

Используется LANCZOS.

Результат:
preview.webp

Изображение сохраняется в WebP lossless, method=6.

16.7. Пирамида уровней

Максимальный уровень:
maxLevel = ceil(log2(max(width, height)))

Создаются уровни от 0 до maxLevel включительно.

Для уровня:
scale = 2^(maxLevel - level)

Размер каждой стороны рассчитывается с округлением вверх. На максимальном уровне используется исходное разрешение.

Каждый уровень формируется из исходного RGBA-изображения с использованием LANCZOS.

16.8. Разделение на тайлы

Размер тайла:
512 × 512 px

Число столбцов:
ceil(levelWidth / 512)

Число строк:
ceil(levelHeight / 512)

Крайние тайлы справа и снизу могут быть меньше 512 пикселей.

Каждый тайл сохраняется в WebP lossless с method=6.

Путь:
public/world-map/versions/<mapVersion>/tiles/<level>/<x>_<y>.webp

Пример:
public/world-map/versions/map-example/tiles/13/0_0.webp

16.9. Координатная система в manifest

Генератор записывает в manifest:
type = minecraft-world-block-centers
minX = -3008
maxX = 3007
minZ = -3008
maxZ = 3007

Эти значения должны соответствовать shared/world-map-coordinates.js основного репозитория.

19. ДИНАМИЧЕСКАЯ ЗАГРУЗКА DEEP ZOOM В БРАУЗЕРЕ
======================================================================

19.1. Принцип

Клиент не загружает все тайлы сразу. Он вычисляет, какая область карты сейчас видна, и запрашивает только тайлы, которые пересекают эту область, с небольшим запасом.

Превью показывается первым и служит базовым изображением. Детальные тайлы накладываются поверх него по мере загрузки.

19.2. Выбор уровня детализации

Используются:
- размеры исходной карты;
- tileSize;
- текущий scale;
- размеры viewport;
- devicePixelRatio;
- minLevel и maxLevel из manifest.

В текущем клиентском коде:
targetPixels = max(viewportWidth, viewportHeight) × devicePixelRatio × scale

idealLevel = maxLevel + log2(targetPixels / max(mapWidth, mapHeight))

Выбранный уровень:
ceil(idealLevel), ограниченный диапазоном minLevel ... maxLevel.

Для devicePixelRatio применяется ограничение сверху 3.

19.3. Вычисление видимых тайлов

Функция:
buildVisibleTiles()

Переводит границы видимой области viewport в нормализованные координаты карты.

Затем вычисляет:
- начальный и конечный X тайлов;
- начальный и конечный Y тайлов;
- URL каждого тайла;
- его положение и размеры на карте.

Добавляется запас примерно в один тайл вокруг видимой области.

19.4. Обновление

Функция:
scheduleTileRefresh()

Откладывает пересчёт примерно на 110 мс после изменений положения/масштаба.

tileSignatureRef хранит подпись списка тайлов. Если список не изменился, лишнее обновление React не выполняется.

В текущей реализации отдельного AbortController для отмены каждого уже начатого HTTP-запроса тайла нет. При смене набора React обновляет набор отображаемых изображений; уже начатая загрузка отдельного изображения может завершиться на уровне браузера.

19.5. Отображение

Тайлы размещаются абсолютными HTML image-элементами внутри слоя карты.

Для изображений используется асинхронное декодирование и высокий приоритет загрузки. Тайлы не перехватывают пользовательские указатели.

Положение и размеры рассчитываются относительно исходного изображения и задаются в процентах.

======================================================================
20. УПРАВЛЕНИЕ КАРТОЙ И МАСШТАБ
======================================================================

20.1. Перемещение

Используются Pointer Events:
- один указатель перемещает карту;
- два указателя запускают pinch-жест.

Трансформация хранится в transformRef.

20.2. Pinch-to-zoom

Для двух указателей вычисляются:
- расстояние между пальцами;
- середина жеста;
- исходный масштаб;
- положение точки карты под серединой жеста.

Отношение нового расстояния к исходному задаёт новый масштаб. Пересчёт смещения сохраняет точку под пальцами.

20.3. Колесо мыши

Поддерживается масштабирование колесом мыши. Изменение масштаба зависит от величины прокрутки и выполняется экспоненциально.

20.4. Ограничения

Реальный масштаб слоя:
1 ≤ scale ≤ 24.

Функции bounds() и clamp() ограничивают смещение так, чтобы карту нельзя было бесконечно увести за пределы viewport.

При scale=1 смещение по X/Y ограничено нулём. При увеличении допустимые границы растут пропорционально масштабу.

20.5. Перерисовка

Трансформация применяется к существующему DOM-слою:
translate(x, y) scale(scale)

Для обновления используется requestAnimationFrame. Это уменьшает количество React-render при движении карты и помогает сохранить чёткость отображения.

Размер маркеров компенсируется через CSS-переменную:
--vox-marker-inverse-scale = 1 / scale

20.6. Пользовательский масштаб

Персональный масштаб задаётся ползунком 1–100%.

Преобразование:
scale = 24 ^ ((100 - percent) / 99)

100% означает исходный масштаб 1x; 1% — максимальное увеличение 24x.

Начальное значение для новых пользовательских настроек:
88%.

Изменение масштаба не меняет диапазон детализации Deep Zoom напрямую: клиент пересчитывает требуемый уровень в зависимости от фактического масштаба карты и плотности экрана.

21. ОБНОВЛЕНИЕ ОПУБЛИКОВАННОЙ КАРТЫ
======================================================================

После загрузки исходника Worker возвращает mapVersion.

Клиент начинает опрашивать manifest:
GET /world-map/manifest.json?check=<timestamp>

Интервал:
5 секунд.

Предельное ожидание в интерфейсе:
25 минут.

Workflow GitHub Actions имеет timeout:
30 минут.

Клиент ждёт, пока manifest.mapVersion совпадёт с ожидаемой версией. После этого:
1. получает previewUrl;
2. загружает и декодирует превью;
3. формирует новый источник карты;
4. устанавливает новую версию;
5. сообщает об обновлении карты.

Пока новая публикация не завершена, предыдущий manifest остаётся доступен. Новая карта считается опубликованной только после успешного обновления статических ресурсов.

Если публикация не завершилась за 25 минут, интерфейс сообщает о проблеме и предлагает проверить workflow.

22. РЕЗЕРВНАЯ ВЫДАЧА ИСХОДНОГО ИЗОБРАЖЕНИЯ
======================================================================

Маршруты:
- HEAD /api/map
- GET /api/map

Backend-функция:
getMapSettings()

D1:
- world_map_github_url;
- world_map_github_content_type.

Worker кэширует настройки ссылки на 30 секунд в памяти экземпляра.

Если ссылка отсутствует:
- HEAD возвращает 404;
- GET возвращает MAP_NOT_UPLOADED.

Если ссылка есть, Worker получает изображение из GitHub Releases и передаёт его клиенту.

Если GitHub возвращает ошибку, Worker повторно читает актуальную ссылку из D1 и пробует получить файл ещё раз. Это помогает, если экземпляр Worker временно использует старый URL.

Ответ содержит соответствующий Content-Type, X-Map-Version, X-Content-Type-Options и cache headers. При доступности upstream также могут передаваться Content-Length и ETag.

Резервный режим не использует Deep Zoom и передаёт целое изображение. Это совместимый путь на случай отсутствия manifest, но не основной способ работы карты.

23. TELEGRAM BOT API И WEBHOOK
======================================================================

23.1. Webhook

Маршрут:
POST /api/webhook

Telegram передаёт Worker обновления:
- обычные сообщения;
- callback_query от inline-кнопок.

Worker использует BOT_TOKEN для вызовов Telegram Bot API.

Дополнительно webhook требует secret header Telegram:
X-Telegram-Bot-Api-Secret-Token

Ожидаемое значение хранится только в Worker secret TELEGRAM_WEBHOOK_SECRET. Значение проверяется до разбора update и до любых действий с D1. При отсутствии или неверном секрете запрос отклоняется; конфигурация без секрета возвращает 503, неверный заголовок — 403. Сравнение выполняется посимвольно без раннего выхода по первому несовпадению.

Telegram должен быть настроен через setWebhook с тем же secret_token и URL https://voxygen.counterboard.workers.dev/api/webhook. Кодовая проверка не активирует секрет на стороне Telegram и не создаёт Worker secret автоматически.

23.2. Callback-сценарии

В webhook обрабатываются, в частности:
- подтверждение/отклонение Minecraft-ника;
- утверждение/отклонение заявки на территорию;
- модерация скриншотов;
- принятие/отклонение приглашения в город;
- голосование по изменению состава управляющих.

Действия, относящиеся к утверждению территории, ограничены главным инспектором.

23.3. Сообщения

28. ОГРАНИЧЕНИЯ И ВАЖНЫЕ ТЕХНИЧЕСКИЕ ОСОБЕННОСТИ
======================================================================

1. Frontend не является источником истины для прав. Все критические проверки выполняются backend.

2. Telegram ID — основной идентификатор аккаунта. Username может меняться и используется как контакт/поисковый атрибут.

3. D1 содержит постоянные данные приложения, но не содержит Deep Zoom-тайлы.

4. Исходная карта хранится в GitHub Release Asset. Ссылка и MIME-тип находятся в app_settings.

5. Публикация новой карты асинхронная. Успешная загрузка исходника ещё не означает, что новая версия уже доступна в клиенте.

6. Версионные URL тайлов позволяют использовать длительное immutable-кэширование.

7. Manifest не кэшируется, чтобы клиент мог обнаружить новую версию.

8. Текущий генератор карты требует квадратный исходник и использует фиксированную геометрию игрового мира.

9. url-grid предусмотрен в контракте, но фактически текущий pipeline публикует Deep Zoom; массив 12×12 ссылок пуст.

10. Legacy fallback /api/map используется клиентом при отсутствии manifest (404), а не при любом сбое manifest.

11. Worker выполняет миграции D1. Ручное изменение таблиц без учёта миграций может привести к несовместимости.

12. Тема в текущем backend ограничена значением vox. Поддержка других тем в UI/данных пока не подтверждена.

13. Общий старый флаг уведомлений сохранён ради совместимости, но актуальные настройки уведомлений разделены по событиям и территориям.

14. В текущей реализации загрузчик Deep Zoom обновляет список отображаемых тайлов по viewport. Отдельной принудительной отмены каждого уже начатого запроса изображения не реализовано.

15. Ошибка авторизации API должна возвращаться как настоящий объект Response (auth.error), а не как внутренняя обёртка { error: Response }. В конечных API-обработчиках это правило соблюдается; requireVerifiedUser и requireMainInspector сохраняют внутреннюю форму результата для вызывающих функций.

16. Активные приглашения имеют уникальность в пределах одной территории и адресата. Для приглашений по Telegram ID и по ещё не сопоставленному Minecraft nickname используются отдельные частичные уникальные индексы.

17. Изменения владельцев и управляющих должны выполняться атомарно через D1 batch. При назначении владельца дополнительно проверяется соответствие owner_input подтверждённой личности пользователя.

18. Одноразовые Telegram-уведомления о приглашениях имеют persisted delivery state и короткую блокировку повторной отправки.

19. Территориальные approval sessions уникальны по inspector_chat_id. В одном чате не может одновременно существовать несколько активных диалогов утверждения.

30. ЗАКЛЮЧЕНИЕ
======================================================================

Voxygen представляет собой модульную Telegram Mini App систему, в которой пользовательский интерфейс, серверная бизнес-логика, постоянные данные и тяжёлые графические ресурсы разделены между отдельными компонентами.

Frontend Worker отвечает за доступность приложения. Основной Worker проверяет Telegram-пользователей, выполняет правила доступа, обслуживает API, работает с D1 и Telegram Bot API. D1 хранит прикладные данные. Отдельный map-assets Worker отдаёт статические графические ресурсы карты.

Ключевая особенность картографической подсистемы — разделение исходной карты и опубликованной пирамиды детализации. Оригинал загружается в GitHub Release, автоматический workflow создаёт preview и WebP-тайлы, а клиент загружает только те уровни и фрагменты, которые нужны текущему viewport.

Остальные подсистемы используют ту же серверную модель: клиент запрашивает действие, backend проверяет пользователя, роль и право на конкретный объект, после чего меняет D1 и при необходимости отправляет уведомления через Telegram.

Такое разделение позволяет развивать интерфейс, серверную логику, экономику и обработку карты независимо, сохраняя единые правила доступа и постоянное хранилище данных.

31. ИСПРАВЛЕНИЯ ПО ИТОГАМ АУДИТА УПРАВЛЕНИЯ ТЕРРИТОРИЯМИ
======================================================================

Этот раздел фиксирует изменения, внесённые в backend после проверки пунктов 30.19–30.32. Он описывает целевое поведение исходного кода main после соответствующих исправлений. Само наличие кода миграции не означает, что миграция уже выполнена в production D1: она выполняется Worker при инициализации схемы после развёртывания.

31.1. Приглашения между территориями

Отмена предыдущего приглашения ограничена той же территорией и тем же адресатом. Приглашения пользователя в других городах сохраняются.

31.2. Защита от повторной отправки приглашений

В city_invites используются notification_sent_at и notification_claimed_at. Перед отправкой Worker атомарно захватывает приглашение; успешная доставка отмечается в D1. При неуспешной доставке действует короткая блокировка, после которой scheduled handler повторяет отправку (не более 50 приглашений за один запуск).

31.3. Истечение голосований

Scheduled handler вызывает expireManagerChangeRequests(). Просроченные manager_change_requests завершаются без необходимости нового нажатия Telegram-кнопки. Обрабатывается ограниченная пачка запросов за один запуск.

31.4. Корректное завершение голосования

finalizeManagerChangeRequest() сначала вызывает applyManagerChange(). Статус approved устанавливается только при успешном применении прав; неудачная операция не фиксируется как одобренная. Условное обновление статуса защищает от повторной финализации.

31.5. Атомарность ролей

applyManagerChange(), updateTerritoryOwner() и updateTerritoryManager() используют D1 batch для связанных изменений владельца, управляющих и членства. После перехода проверяется фактическое состояние записей.

31.6. Дубликаты приглашений

Миграция v28 сначала закрывает уже существующие повторяющиеся pending-приглашения, затем создаёт частичные уникальные индексы:
- территория + target_telegram_id для приглашений зарегистрированным пользователям;
- территория + lower(target_nickname) для приглашений, адресат которых ещё не сопоставлен.

31.7. Удаление территории

Удаление территории пакетно удаляет связанные manager_change_votes, manager_change_requests, approval session, членство, управляющих, городские предметы и оформление; ожидающие приглашения переводятся в cancelled. Запись территории удаляется последней в том же D1 batch.

31.8. Создание заявки

Для обычной заявки наличие INSPECTOR_CHAT_ID проверяется до INSERT. Если Telegram не принимает уведомление или отправка завершается ошибкой, созданная pending-территория удаляется компенсирующей операцией. Прямое создание главным инспектором остаётся отдельным сценарием.

31.9. Первичное назначение владельца

claimTerritoryOwner() требует подтверждённый Minecraft nickname и совпадение owner_input с Minecraft nickname или Telegram username. UPDATE выполняется только при owner_telegram_id IS NULL. Одновременные попытки не могут перезаписать владельца друг друга.

31.10. Сессии утверждения

Для inspector_chat_id создан уникальный индекс. Перед запуском новой сессии в том же чате предыдущая сессия удаляется; миграция сохраняет наиболее свежую сессию среди старых дубликатов.

31.11. Устойчивость утверждения к сбоям Telegram

После изменения статуса территории в approved сначала выполняются локальные post-processing операции. Итоговое Telegram-сообщение отправляется последним и обрабатывается отдельно; ошибка уведомления не прерывает уже сохранённое утверждение.

31.12. Позднее сопоставление владельца

Если на момент утверждения владелец не найден среди verified users, owner_input сохраняется. При последующем входе подходящего подтверждённого пользователя Worker проверяет уникальность совпадения по Minecraft nickname или Telegram username и может привязать владельца условным UPDATE. Переназначение orphan-владельца и очистка связанных отношений выполняются в одном D1 batch.

31.13. Удаление пользователя и старые приглашения

При удалении управляемого пользователя ожидающие приглашения, где он является адресатом или инициатором, переводятся в cancelled. Callback обработчик также проверяет наличие verified-профиля адресата до создания city_memberships.

31.14. Контракт ошибок авторизации

52 конечных API-обработчика возвращают auth.error как Response. Внутренние requireVerifiedUser() и requireMainInspector() продолжают передавать структуру auth вызывающим функциям; эти два места намеренно не заменяются.

31.15. Проверки

Для неавторизованных запросов добавлены проверки маршрутов обычного пользователя, главного инспектора и пользователя с обязательным подтверждённым Minecraft nickname. GitHub Actions запускает npm test, npm run build, node --check и Wrangler dry-run при обновлении main и при pull request в main.



======================================================================
32. ИСПРАВЛЕНИЯ ПО ИТОГАМ АУДИТА ЭКОНОМИКИ, СОБЫТИЙ И API
======================================================================

Этот раздел описывает исправления, внесённые после аудита подсистем авторизации, рейтингов, комментариев, скриншотов и Telegram-банковских операций.

32.1. Срок действия Telegram Init Data

verifyInitData() после проверки HMAC проверяет auth_date. Принимаются только данные не старше 24 часов; допустимое отклонение времени в будущее — не более 60 секунд. Отсутствующий или просроченный auth_date приводит к отказу в авторизации.

32.2. Защита ограничения частоты оценок

Ограничение в 20 часов дополнительно встроено непосредственно в ON CONFLICT DO UPDATE ... WHERE. Даже если два запроса одновременно прошли предварительное чтение, только один из них может обновить запись оценки.

32.3. Комментарии и ответы

Редактирование ответа ограничено теми же 4000 символами, что и создание. Создание ответа использует INSERT OR IGNORE с проверкой существования комментария; уведомление об ответе отправляется только при фактическом первом создании записи. Удаление комментария и его ответа объединено в один D1 batch.

32.4. Одноразовая модерация скриншотов

Callback-кнопки и HTTP API обновляют скриншот только при текущем статусе pending. Условный UPDATE предотвращает повторное изменение статуса по устаревшей кнопке. HTTP POST /api/screenshots/{id} требует явного решения approve или status.

32.5. Атомарность Telegram-банковских операций

Изменение user_currency или city_treasury и фиксация статуса/остатка в bank_transactions выполняются одной D1 batch-транзакцией. Повторная обработка update_id разрешена только для незавершённой записи processing; условие статуса в запросе баланса гарантирует, что один update_id не проведёт перевод повторно. Обработчик ошибки не перезаписывает уже завершённую операцию.

32.6. Инициализация таблиц публичных read API

GET-маршруты рейтингов, комментариев и скриншотов вызывают ensureWorldTables() перед чтением. Это предотвращает ошибку отсутствующей таблицы, если один из этих маршрутов является первым запросом после развёртывания Worker.

32.7. Регрессионные проверки

Добавлены tests/security-and-bank.test.js:
- корректная подпись и свежий auth_date;
- отказ для просроченного, будущего и отсутствующего auth_date;
- разбор поддерживаемых вариантов банковской команды;
- успешный банковский перевод и безопасный повтор;
- отказ при недостаточном балансе без изменения остатка.

GitHub Actions проверяет npm test, npm run build, node --check bot/src/worker.js и Wrangler deploy --dry-run.



32.8. Атомарность покупки визуала и каталога

Покупка визуала теперь включает списание, выдачу предмета и запись gem_spend_log в одном D1 batch. Это предотвращает ситуацию, когда покупка состоялась, но расход не попал в расчёт городского достижения. Проверка первого маркера и пересчёт достижений выполняются после фиксации покупки как best-effort операции. Удаление визуала объединяет очистку city_customization, city_items и деактивацию предмета в одном batch. Ошибка последующей очистки или пересчёта не возвращает ложный отказ уже выполненной операции.

32.9. Устойчивость каталога

При создании и редактировании визуала синхронизация государственных предметов и пересчёт достижений выполняются как best-effort post-processing: сбой этих вспомогательных шагов не превращает уже сохранённое изменение каталога в ошибку для клиента. При редактировании сервер повторно проверяет допустимый цвет предмета.

32.10. События и напоминания

Удаление события и отмена его ожидающих/отправляемых напоминаний выполняются одним D1 batch. Обновление события ограничено активными событиями и проверяет фактическое изменение записи; пересчёт напоминаний также требует, чтобы событие оставалось активным. Очистка старых событий, напоминаний и ключей создания выполняется одним batch. Обработчики создания, редактирования и удаления события инициализируют основную схему до обращения к таблице inspectors для проверки роли.

32.11. Автоматическое одобрение скриншотов

Если скриншот сразу получает статус approved при загрузке инспектором, backend запускает пересчёт достижений после сохранения. Ранее этот путь обходил обработчики модерации и мог не учитывать новый скриншот в достижении.

32.12. Повтор банковского webhook

При внутренней ошибке незавершённая банковская запись остаётся в processing, а webhook возвращает HTTP 500, чтобы Telegram мог повторить доставку update. Повтор безопасен благодаря атомарной операции баланса и журнала. Уже завершённая запись не может быть перезаписана статусом failed.


32.13. Согласованность интерфейса инвентаря

CustomizationScreen отслеживает состав доступных счетов по ID территорий, а не только по их количеству. Ответы старых запросов полной загрузки и обновления баланса игнорируются, если пользователь уже переключился на другой счёт. Это предотвращает отображение инвентаря или баланса предыдущей территории после быстрой смены счёта.

33. ПОДРОБНЫЙ АУДИТ КАРТОГРАФИЧЕСКОЙ ПОДСИСТЕМЫ
======================================================================

Раздел фиксирует повторную проверку полной цепочки карты: загрузку исходника, хранение, запуск GitHub Actions, генерацию Deep Zoom, публикацию статических ресурсов, manifest, клиентский выбор тайлов, кэширование и обработку ошибок. Описание относится к исходному коду main двух репозиториев; состояние Cloudflare production отдельно оговаривается в подразделе 33.11.

33.1. Состав компонентов

Картографическая подсистема состоит из следующих независимых частей:

1. Frontend:
   - src/App.jsx;
   - административная функция saveMap() в панели главного инспектора;
   - waitForPublishedMap();
   - loadWorldMap();
   - компонент VoxMap;
   - shared/world-map-coordinates.js.

2. Основной backend:
   - bot/src/worker.js;
   - POST /api/map → saveMapSettings();
   - GET/HEAD /api/map → getMapSettings();
   - D1 app_settings;
   - GitHub Release API и GitHub Actions API.

3. Pipeline:
   - репозиторий CounterBoard/Voxygen-map-assets;
   - .github/workflows/publish-map.yml;
   - tools/download_release_asset.py;
   - tools/build_map.py;
   - public/world-map/;
   - public/_headers;
   - Wrangler Static Assets Worker voxygen-map-assets.

4. Хранилище исходников:
   - CounterBoard/Voxygen-map-storage;
   - Release tag world-map;
   - Release Assets с исходными PNG/JPEG/WebP файлами.

В D1 не хранятся исходные байты карты, preview или Deep Zoom-тайлы. В app_settings остаются только URL актуального GitHub Release Asset и его MIME-тип. Опубликованные тайлы размещаются в статическом каталоге отдельного Worker.

33.2. Загрузка карты из интерфейса

Функция saveMap(file) выполняется в панели главного инспектора.

Проверки на клиенте:
- MIME-тип должен быть image/png, image/jpeg или image/webp;
- размер должен быть больше нуля и не превышать 90 000 000 байт;
- реальные размеры изображения читаются через Image и URL.createObjectURL();
- ширина и высота должны совпадать;
- фронтенд не уменьшает исходный растр перед отправкой.

Передача:
- метод POST;
- адрес https://voxygen.counterboard.workers.dev/api/map;
- Content-Type содержит MIME-тип файла;
- X-Telegram-Init-Data содержит Telegram Web App Init Data;
- X-Map-Size содержит File.size;
- используется XMLHttpRequest, чтобы показывать upload progress;
- таймаут XHR — 600 000 мс;
- обрабатываются сетевой сбой, таймаут и отмена запроса.

После ответа Worker интерфейс ожидает mapVersion. Затем сохраняет в localStorage ключ voxygen:map-publication-pending с версией и временем начала и начинает проверять публикацию. Если ожидание завершилось по таймауту, запись остаётся и проверка может быть возобновлена при следующем открытии панели.

33.3. Серверная проверка и передача в GitHub Release

saveMapSettings() сначала вызывает requireMainInspector(). Клиентская роль не считается достаточным подтверждением административного доступа.

Проверяются:
- MIME-тип;
- X-Map-Size или Content-Length;
- корректность целого безопасного положительного размера;
- совпадение Content-Length с заявленным размером, если Content-Length доступен;
- верхний предел 90 000 000 байт;
- наличие request.body;
- GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO;
- MAP_PIPELINE_GITHUB_TOKEN.

Для имени Asset используется:
voxygen-world-map-<timestamp>.<extension>

Соответствие расширения:
- image/png → png;
- image/jpeg → jpg;
- image/webp → webp.

Основной Worker:
1. получает Release по тегу world-map;
2. извлекает upload_url;
3. создаёт FixedLengthStream ожидаемой длины;
4. одновременно передаёт request.body в поток и отправляет поток в GitHub Release Assets API;
5. проверяет результат GitHub и наличие browser_download_url;
6. сохраняет browser_download_url и MIME-тип в app_settings;
7. вычисляет mapVersion из имени файла без расширения;
8. вызывает workflow_dispatch репозитория CounterBoard/Voxygen-map-assets;
9. после успешного запуска pipeline выполняет очистку достаточно старых исходных image Assets.

Сохранение исходного Asset и его публикация в map-assets — разные этапы. Ответ основного Worker с processing = queued означает, что исходник загружен и workflow поставлен в очередь, а не то, что manifest уже обновлён.

Для очистки исходников действует retention window 48 часов. Недавние Assets сохраняются, чтобы queued workflow успел скачать нужный исходник. Ошибки удаления старых Assets логируются отдельно и не отменяют уже поставленную обработку.

33.4. D1 и резервная выдача исходника

Ключи app_settings:
- world_map_github_url;
- world_map_github_content_type.

Старые ключи прежней системы хранения очищаются:
- world_map_object_key;
- vox_map_image;
- jorick_map_image.

getMapSettings():
- использует cache в памяти изолята Worker с TTL 30 секунд;
- при отсутствии URL возвращает 404;
- для HEAD при отсутствии карты возвращает пустой 404;
- скачивает исходник из GitHub Release с redirect: follow;
- если upstream недоступен, перечитывает URL из D1 один раз, чтобы учесть обновление из другого Worker isolate;
- возвращает Content-Type, Content-Length при наличии, ETag при наличии, X-Map-Version и X-Content-Type-Options: nosniff;
- использует Cache-Control public, max-age=31536000, immutable только когда query-параметр v совпадает с текущей версией; без совпадения применяется max-age=300;
- добавляет Server-Timing и CORS.

Этот маршрут — legacy fallback, а не основной источник карты после появления manifest.

33.5. Запуск workflow и безопасная загрузка исходника

Основной Worker вызывает:
POST https://api.github.com/repos/CounterBoard/Voxygen-map-assets/actions/workflows/publish-map.yml/dispatches

Передаются:
- ref = main;
- inputs.image_url = browser_download_url загруженного Release Asset;
- inputs.map_version = mapVersion.

Токен MAP_PIPELINE_GITHUB_TOKEN используется только для GitHub Actions API и не передаётся в URL исходного изображения.

В pipeline используется tools/download_release_asset.py. Его проверки:
- URL должен быть HTTPS;
- hostname должен быть github.com;
- путь должен вести именно к CounterBoard/Voxygen-map-storage/releases/download/<tag>/<asset>;
- запрещены query, fragment, userinfo, нестандартный порт и лишние сегменты пути;
- redirect разрешён только на allowlist GitHub asset hosts;
- redirect должен быть HTTPS;
- дополнительная цепочка redirect запрещена;
- GitHub API token не пересылается на asset host;
- Content-Length, если есть, проверяется;
- фактически скачанные байты ограничены 90 000 000;
- пустой файл отклоняется;
- частичный файл удаляется при ошибке.

Allowlist download hosts в коде:
- objects.githubusercontent.com;
- release-assets.githubusercontent.com;
- github-production-release-asset-2e65be.s3.amazonaws.com.

После скачивания файл всё равно проходит проверку декодером Pillow при сборке. URL-проверка не заменяет проверку формата и размеров изображения.

33.6. Генератор Deep Zoom

Файл: tools/build_map.py.

Константы:
- TILE_SIZE = 512;
- PREVIEW_MAX = 1200;
- MAX_RASTER_DIMENSION = 8944;
- MAX_RASTER_PIXELS = 80 000 000.

Ограничения проверяются по размерам заголовка изображения до преобразования в RGBA. Pixel budget согласован с защитным лимитом Pillow от decompression bomb. Для квадратного растра 8944×8944 содержит 79 995 136 пикселей и укладывается в лимит; большая сторона или общий pixel count отклоняются.

Порядок:
1. проверяет количество аргументов командной строки;
2. проверяет MAP_VERSION;
3. разрешает в версии только латинские буквы, цифры, точку, подчёркивание и дефис;
4. открывает изображение и проверяет фактический формат Pillow: PNG, JPEG или WebP;
5. читает исходные width/height;
6. проверяет каждую сторону в диапазоне 1–8944;
7. проверяет width × height ≤ 80 000 000;
8. требует квадратный растр;
9. применяет ImageOps.exif_transpose();
10. переводит проверенный растр в RGBA;
11. строит preview с максимальной стороной 1200 и фильтром LANCZOS;
12. вычисляет maxLevel = ceil(log2(max(width, height)));
13. строит уровни от 0 до maxLevel включительно;
14. на каждом уровне уменьшает исходный растр в степени двойки;
15. режет уровень на тайлы не более 512×512;
16. сохраняет каждый тайл как lossless WebP с method=6;
17. формирует manifest;
18. записывает manifest во временный файл и заменяет им world-map/manifest.json после генерации тайлов.

Для уровня:
reduction = 2 ** (maxLevel - level)
levelWidth = ceil(width / reduction)
levelHeight = ceil(height / reduction)
columns = ceil(levelWidth / 512)
rows = ceil(levelHeight / 512)

Имена тайлов:
<level>/<x>_<y>.webp

Индексы начинаются с нуля. Последние тайлы по правой и нижней границе могут быть меньше 512 пикселей. Генератор не добавляет padding до полного размера.

Генератор использует неизменную геометрию мира, а не вычисляет её из разрешения картинки. Поэтому квадратность растра обязательна для равного масштаба X/Z, но конкретное разрешение не обязано равняться 6016×6016.

33.7. Формат manifest и версионные ресурсы

Путь manifest:
GET /world-map/manifest.json

Поля верхнего уровня:
- schemaVersion;
- mapVersion;
- source;
- futureSources;
- generated.

Для действующего source.type = deepzoom используются:
- width;
- height;
- tileSize;
- minLevel;
- maxLevel;
- format;
- coordinateSystem;
- tileUrlTemplate;
- previewUrl.

coordinateSystem:
- type = minecraft-world-block-centers;
- minX = -3008;
- maxX = 3007;
- minZ = -3008;
- maxZ = 3007.

URL ресурсов содержат версию:
- /world-map/versions/<mapVersion>/preview.webp;
- /world-map/versions/<mapVersion>/tiles/<level>/<x>_<y>.webp.

Версия в пути делает содержимое конкретного preview/тайла неизменяемым. Manifest, наоборот, должен оставаться без кэша, чтобы клиент мог обнаружить новую публикацию.

futureSources.urlGrid зарезервирован для 12×12 сетки и 144 URL. В текущем генераторе urls остаётся пустым. Клиентская ветка url-grid есть, но действующий pipeline создаёт только Deep Zoom.

33.8. Загрузка manifest и preview в клиенте

loadWorldMap():
1. увеличивает mapLoadGenerationRef;
2. запрашивает manifest с cache: no-store и дополнительным cache-busting query;
3. игнорирует результат, если поколение загрузки уже устарело;
4. проверяет mapVersion и допустимый source.type;
5. для Deep Zoom проверяет положительные конечные width/height;
6. проверяет coordinateGeometryMatchesManifest();
7. получает previewUrl из source.previewUrl или manifest.previewUrl;
8. разрешает относительный путь относительно MAP_ASSETS_BASE;
9. декодирует preview;
10. устанавливает preview как основное изображение-подложку и source с assetBase/mapVersion.

Fallback:
- только HTTP 404 на manifest приводит к проверке legacy /api/map;
- невалидный manifest, HTTP 500, ошибка JSON или ошибка preview не обходятся legacy fallback;
- legacy запрос выполняет HEAD, проверяет Content-Type и X-Map-Version, затем загружает изображение по GET URL с v=version.

Такой порядок не позволяет молча заменить сломанную новую публикацию старым исходником, если manifest уже существует, но повреждён или несовместим.

33.9. Выбор тайлов и обработка viewport

VoxMap() поддерживает source.type deepzoom и url-grid.

Для Deep Zoom:
- viewport dimensions берутся из DOM;
- текущая матрица карты задаёт x, y и scale;
- видимая область переводится в нормализованные границы 0..1;
- devicePixelRatio ограничивается 1..3;
- targetPixels рассчитывается из размера viewport, DPR и масштаба;
- идеальный уровень выбирается относительно maxLevel и размера исходного растра;
- итоговый уровень округляется вверх и ограничивается minLevel/maxLevel;
- координаты тайлов вычисляются по tileSize;
- к видимой области добавляется запас в один тайл по краям;
- placeholder level/x/y подставляются в tileUrlTemplate;
- относительный URL разрешается относительно assetBase;
- CSS-позиция и размер тайла рассчитываются в процентах от полного изображения уровня.

Для url-grid:
- используется rows/columns;
- URL выбирается из urls[y * columns + x];
- URL может быть абсолютным или относительным к assetBase;
- непустые URL превращаются в прямоугольники сетки.

Производительность:
- pointer gesture напрямую меняет transform существующего DOM-слоя;
- paintTransform вызывается через requestAnimationFrame;
- список тайлов обновляется с debounce около 110 мс;
- viewState синхронизируется с родителем после жеста или через короткую задержку;
- при смене source старый список тайлов очищается;
- при resize viewport пересчитываются границы и список тайлов;
- маркеры используют обратный масштаб, чтобы сохранять визуальный размер при увеличении карты.

Preview остаётся нижним слоем. Если отдельный тайл не загрузился, он не перекрывает всю карту и в соответствующей области остаётся preview. Отдельного интерфейсного сообщения о сбое конкретного тайла нет. Отдельный AbortController для уже начатых img-запросов не используется.

34.5. Операционный порядок дальнейшей проверки

Граница надёжности POST /api/map после дополнительного исправления:
- Worker загружает исходник в GitHub Release;
- формирует mapVersion из имени asset;
- вызывает workflow_dispatch publish-map.yml;
- при ответе GitHub не 204 возвращает 502 и НЕ записывает новый URL/content type в D1;
- только после подтверждённого dispatch (HTTP 204) Worker атомарно записывает world_map_github_url и world_map_github_content_type в D1 batch и удаляет legacy keys;
- таким образом, отказ dispatch больше не оставляет D1 с URL нового, но необработанного изображения.

Остаточная граница: GitHub может принять dispatch (204), после чего D1 batch может завершиться ошибкой. В таком редком случае workflow уже запущен, но legacy D1 URL не обновлён. Это не откатывает опубликованный manifest; manifest-first клиент продолжает читать опубликованную карту. Полная компенсация этого распределённого шага (outbox/reconciliation) и конкурентные integration tests для нескольких одновременных загрузок остаются отдельной задачей.

Для завершения runtime-проверки карты следует:
1. проверить актуальный manifest прямым GET;
2. разобрать все URL и проверить доступность preview;
3. проверить по одному тайлу низкого, среднего и максимального уровня;
4. сравнить размеры и tileCount manifest с фактически опубликованными файлами;
5. проверить Cache-Control, CORS и Content-Type на manifest, preview и tile;
6. загрузить тестовую карту через UI только после согласования production изменения;
7. проверить появление новой mapVersion и завершение публикации;
8. убедиться, что legacy /api/map не используется при существующем корректном manifest;
9. проверить поведение при HTTP 404, 500 и некорректном manifest в отдельном тестовом окружении.

До отдельного согласования эти действия не включают production upload новой карты, изменение production D1 или deploy Cloudflare Worker.


34.6. Защита Telegram webhook

В ходе расширенного аудита обнаружено, что обработчик POST /api/webhook ранее принимал JSON update без проверки Telegram secret header. Это позволяло внешнему клиенту отправить поддельный callback_query и подставить Telegram ID, который backend сопоставляет с ролью. Проверка роли внутри callback не заменяет аутентификацию самого webhook.

Исправление в bot/src/worker.js:
- добавлена проверка TELEGRAM_WEBHOOK_SECRET;
- читается X-Telegram-Bot-Api-Secret-Token;
- допустимый secret соответствует Telegram charset A-Z, a-z, 0-9, underscore, hyphen, длина 1–256;
- отсутствующий/некорректно настроенный Worker secret приводит к HTTP 503;
- неверный или отсутствующий request header приводит к HTTP 403;
- сравнение одинаковых по длине строк выполняется через накопление XOR-разницы, без раннего выхода по символам;
- проверка выполняется до request.json(), до запросов D1 и до выполнения callback/message handlers;
- секрет и его части не записываются в логи.

Добавлен tests/webhook-security.test.js. Проверяются:
1. fail-closed при отсутствии TELEGRAM_WEBHOOK_SECRET;
2. отказ при отсутствии header;
3. отказ при неправильном header;
4. отказ при недопустимом формате настроенного секрета;
5. успешный проход в webhook при правильном заголовке.

Операционное условие: кодовая проверка сама по себе не устанавливает secret в Cloudflare и не вызывает Telegram setWebhook. До deployment нужно установить Worker secret TELEGRAM_WEBHOOK_SECRET и зарегистрировать Telegram webhook с идентичным secret_token. Production конфигурация и Telegram webhook в рамках этого аудита не менялись. Поэтому до установки обоих значений и deployment нельзя считать защиту активной в production.


34.7. Публичные read-only маршруты и авторизация

При проверке маршрутизатора важно отличать публичное чтение данных от незащищённой записи. Следующие GET-маршруты предназначены для чтения публичной части приложения:
- /api/health и /;
- /api/territories — только утверждённые территории;
- /api/events — активные события и события в пределах последнего 24-часового окна; параметр manage=1 требует главного инспектора;
- /api/ratings и /api/comments — чтение по territoryId;
- /api/screenshots — только approved;
- /api/screenshots/{id} — только approved;
- /api/faq;
- /api/recruitment;
- /api/map — резервная выдача исходной карты;
- /api/vox-grid — публичное чтение сетки; поле canEdit рассчитывается отдельно;
- /api/customization/items/{id}/image — выдача изображения визуала по ID.

Записи и административные изменения должны проходить серверные проверки:
- requireUser — обычная авторизация Telegram;
- requireVerifiedUser — авторизация плюс подтверждённый профиль Minecraft;
- requireMainInspector — административная роль;
- POST /api/territories отдельно проверяет Telegram Init Data через verifyInitData() и для обычного пользователя требует подтверждённый Minecraft nickname.

Webhook выделен отдельно: он не использует Telegram Init Data, поэтому для него обязательна проверка X-Telegram-Bot-Api-Secret-Token, описанная в 34.6.

Публичный read-only маршрут не следует считать доступом к приватным данным автоматически: например, список скриншотов и выдача файла ограничены статусом approved. Для ratings/comments доступность определяется наличием territoryId и данными таблиц; эти маршруты не требуют авторизации.

До аудита workflows использовали npx wrangler@latest. Это делало dry-run и production map-assets deployment зависимыми от версии CLI, опубликованной в npm в момент запуска, и могло неожиданно изменить поведение без изменения исходников.

Исправлено:
- .github/workflows/validate.yml основного приложения использует wrangler@4.162.0;
- .github/workflows/publish-map.yml репозитория CounterBoard/Voxygen-map-assets также использует wrangler@4.162.0;
- версия CLI теперь одинаковая в обоих workflows и не плавает вслед за latest;
- это pin версии CLI, но не полная фиксация цепочки npm dependencies: основное приложение пока не имеет package-lock.json, CI выполняет npm install, а Python workflow ставит Pillow/requests через pip upgrade. Полная воспроизводимость потребует lock-файлов и закрепления зависимостей.

34.11. CORS и cache contract map-assets

public/_headers определяет две разные политики:
- /world-map/manifest.json: Access-Control-Allow-Origin: *, GET/HEAD/OPTIONS, разрешён Content-Type и If-None-Match, nosniff, Cache-Control: no-store;
- /world-map/versions/*: Access-Control-Allow-Origin: *, GET/HEAD/OPTIONS, Content-Type и If-None-Match, nosniff, Cache-Control: public, max-age=31536000, immutable.

Manifest нельзя кешировать надолго, поскольку он является указателем на текущую mapVersion. Версионные preview и tiles не меняются внутри version path и безопасны для долгого immutable cache.

Добавлен tests/test_static_headers.py:
- проверяет CORS и no-store manifest;
- проверяет CORS, nosniff и immutable cache для versioned assets.

Последний map-assets CI:
- run id 43571388934;
- commit afecbbef83dc84b7ad950034cee9e17ba4883740;
- 15 Python tests passed.

Проверка _headers unit test подтверждает содержимое конфигурации, но не фактические response headers Cloudflare edge. Production CORS/cache по-прежнему требуют HTTP runtime probe.

34.12. Пересчёт Deep Zoom при изменении viewport

В WorldMap visible tile set вычисляется из viewport.clientWidth/clientHeight, текущего pan/scale и devicePixelRatio. До исправления пересчёт запускался при жестах (pan, pinch, wheel), но не при изменении размера viewport без жеста. При повороте устройства, изменении высоты панели или responsive resize могла оставаться старая выборка тайлов: preview продолжал отображаться, но высокодетализированные тайлы не покрывали новую область.

Исправлено в src/App.jsx:
- добавлен ResizeObserver на map viewport;
- при resize вызывается scheduleTileRefresh(), существующий debounce 110 ms объединяет частые resize события;
- observer отключается в cleanup;
- если ResizeObserver отсутствует, прежний preview и ручной пересчёт сохраняют работоспособность.

Изменение затрагивает только клиентский tile selection, не координаты территорий и не map manifest. Проверка CI подтверждает синтаксис/build, но поведение при реальном Android orientation change требует browser/WebView runtime test.
